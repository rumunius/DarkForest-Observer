### 1.2 已确认的实施边界

1. 日常开发、调试和前后端联调在本地进行，不要求持续访问 Cloudflare 云端业务资源。首次安装依赖、查阅资料、重新登录及阶段部署可能需要联网。
2. 架构继续采用 Pages 静态前端 → Pages Functions 同源HTTP → 独立 Worker 中的单场 SQLite-backed Durable Object。每场仅一个确定性权威对象。
3. 不新增 D1、KV、R2 或外部数据库作为比赛状态源，不把浏览器模拟状态升级为正式规则引擎。
4. 不恢复网站地图、经纬度、位置轨迹、照片上传和高德解析。照片与终局共享位置留在QQ，网站只保存玩家声明、审核和裁决。
5. 正常出航者可读取本人现役配置；赛中观战需永久淘汰满180秒，并可读取完整已发生战况；完赛后本场正式参赛者立即可读完整复盘。未来随机计划、原始抽签值、认证材料不进入这些投影。
6. 大屏使用现有裁判会话，通过专用只读接口返回观战范围数据，不增设大屏口令或将完整裁判后台返回给大屏。
7. 本场目击超过120次后继续按正常门禁受理，只向裁判告警；不因该阈值增加个人禁攻。技术爆炸排除退出正式名单和已永久淘汰者，合法返航及重生准备者仍可参加抽取。

### 1.3 第一版完成范围

可用于正式赛事的第一版应包含全部核心比赛流程、广播/歌者/技术爆炸/光粒、基础裁判GUI及控制台、通知队列、权限投影、完整复盘、常见纠错和恢复演练。不能将“目击接口跑通”或“P0完成”解释为已具备正式开赛条件。

复杂条件命令、命令宏、任意组合批处理和依赖场地几何的区域效果不作为首版前置条件。技术方案§15.6已允许按阶段扩展控制台；常用裁判能力仍须有可验收的受保护入口。

## 3. 本地开发、preview与生产的工作方式

### 3.1 日常本地链路

```text
浏览器 → Vite :5173 → /api代理 → Wrangler Pages :8788
                                      ↓ MATCH_DO 本地绑定
                              Wrangler Worker :8787
                                      ↓
                            本地DO SQLite与Alarm
```

使用现有 `npm run dev`启动三进程。Wrangler默认本地运行，禁止在日常脚本中加入 `--remote` 或 `remote: true` 来接入真实比赛资源。本地Worker名称和Pages的 `script_name`必须一致。

| 命令                        | 当前用途                                   | 本计划要求                                        |
| --------------------------- | ------------------------------------------ | ------------------------------------------------- |
| `npm ci`                    | 安装锁定依赖                               | 首次或锁文件变化后执行，无需每轮联调重装          |
| `npm run dev`               | 构建前端并启动core、pages、web             | 后端联调主入口；启动后核验本地DO绑定及实际RPC     |
| `npm run dev:preview`       | 只启动前端模拟预览                         | 保留用于UI演示，不作为后端验收证据                |
| `npm run check`             | 格式、lint、类型、前端构建、Worker dry-run | 本地检查，不应上传部署；不替代业务测试            |
| `npm run test`              | 当前运行单元测试                           | 后续明确单元与Workers测试入口，保证真实用例数非零 |
| `npm run cf:preview:deploy` | 先部署preview Worker，再部署Pages的dev分支 | 只在里程碑本地验收通过后执行                      |

本地状态使用根目录 `.wrangler/state/`；自动化测试使用独立存储路径与测试场次，不能清空开发者手动联调的数据库。常规重启应保留状态；重置、重新播种和迁移回归应是显式工具动作。

实现本地初始化工具，建立虚构玩家、三个独立裁判账号及可重建的测试场次。账号发放文件进入被忽略的私有目录；Git中只保留无真实凭证的模板和生成逻辑。测试加速时间、固定随机源及故障注入仅供测试装配，不接收浏览器请求中的“当前时间”“抽签结果”或调试Header。

### 3.2 三环境隔离

| 项目       | local                   | preview                                     | production                                |
| ---------- | ----------------------- | ------------------------------------------- | ----------------------------------------- |
| Worker     | `darkforest-core-local` | `darkforest-core-preview`                   | 上线阶段建立独立生产Worker                |
| Pages      | Wrangler本地实例        | 现配置 `darkforest-pages-dev` 的 `dev` 分支 | 建议独立生产Pages项目，名称在上线阶段确定 |
| SQLite     | 本机持久化目录          | preview Worker的独立DO命名空间              | 独立生产命名空间                          |
| 场次       | 本地虚构场次            | 各轮验收使用独立 `match_id`                 | 新建正式场次，禁止导入排练战局            |
| 密钥、账号 | 本地专用                | preview专用                                 | 正式专用，不复用前两者                    |
| 数据来源   | 合成数据                | 合成数据或经确认的排练数据                  | 正式名册与审核数据                        |

当前仓库没有生产配置和生产部署脚本，以上production列是实施目标。选择独立生产Pages项目属于环境组织建议，不改变既定Pages架构；正式资源创建前落实资源名称与目标账户。

Pages的历史preview URL并不天然拥有独立数据库或固定的Worker版本。同一preview Worker和同一 `match_id`会共享战局；验收记录必须注明Pages部署、Worker版本、schema及场次，不能把旧URL当作整套后端回滚点。

### 3.3 云端验收的必要范围

本地负责规则、事务、重试、并发、权限、重启和大部分端到端联调。preview负责验证真实Bindings/RPC、Secrets、HTTPS Cookie、部署迁移、无人访问Alarm、实际手机及校园网络访问、平台额度和部署兼容性。

每个主要里程碑集中发布一次；发现云端差异后回本地修复，再发布复验。开发中不反复部署单个按钮、表单或小段SQL。

现工程文档记录的preview入口为 `https://dev.darkforest-pages-dev.pages.dev/`。本次没有查询该项目的当前部署、登录状态、账户额度或在线功能；首次里程碑发布前重新核验。CLI能够完成的配置由开发流程处理，需要网页授权、Access策略、域名或DNS操作时再给用户具体步骤。

## 4. 后端模块和权威边界

建议沿用现有目录，按实际业务拆分，避免先引入大量通用框架。

| 模块                         | 职责与边界                                                                              |
| ---------------------------- | --------------------------------------------------------------------------------------- |
| `packages/contracts/src/`    | 公开DTO、严格请求Schema、颜色与展示参数、动作和错误码；浏览器不导入服务端存储与密钥模块 |
| `apps/web/functions/api/`    | 同源路由、请求体大小、Content-Type、Origin/CSRF、Cookie、可信入口UTC、响应头及DTO封装   |
| `apps/match-worker/src/rpc/` | 受控内部调用参数；读、写、登录及引导操作分别列白名单，不提供任意方法名调用              |
| `domain/`                    | 状态机、时间计算、合法码、结果分类、资格、排名等可独立验证的规则                        |
| `services/`                  | 统一业务授权、到期屏障、幂等与事务编排；GUI和控制台复用相同服务                         |
| `storage/`                   | schema迁移、参数化SQL、仓储、约束、持久版本与一致性检查                                 |
| `scheduler/`                 | 持久化事件队列、双时基映射、到期结算、单Alarm重排和调度健康                             |
| `projections/`（新增）       | public、self、observer、display、judge和results各自的字段白名单                         |
| `security/`（新增）          | 凭证与会话摘要、CSRF、HMAC/AES-GCM、安全随机及密钥版本                                  |

Pages不得信任客户端给出的 `player_id`、角色、阶段或场次。首版由服务端环境配置选择可登录场次；登录后会话绑定场次，DO再次核验身份、角色和资源范围。场次ID即使进入Cookie路由材料，也必须经过服务端完整性验证并与DO会话对应，不能允许浏览器任意选择权威对象。

构造函数仅执行幂等schema初始化和必要读取。比赛、账号和T0/T1由显式引导与受权业务操作建立，不以对象首次被访问的时间自动开赛。

## 5. 数据、事务、幂等和时间设计

### 5.1 迁移与持久化

按技术方案§4.3逐模块迁移比赛、玩家、母星、航次、码本、攻击、情报、事件、淘汰、暂停、通知、会话、审计和调度表。首版一并补充必要辅助结构：

- 账号凭证摘要、裁判账号与细粒度授权、会话撤销及CSRF绑定。
- 比赛/实体版本、通知乐观锁版本、活动配置版本、结果归档与报告版本。
- 预览令牌及其作用范围、操作恢复状态；schema中的字段名与HTTP DTO通过显式映射隔离。
- 观战禁用/恢复的管理记录，落实策划案§7.7违约后撤销观战的能力；180秒并非唯一授权条件。
- 码的激活UTC及竞速关联证据、事件生效与提交时间、可追踪的纠错历史。

昵称先统一Unicode正规化，再做2—8个可见字符、不可见控制字符、唯一性和锁定校验。具体字符计数、拉丁字母大小写等归一化规则在M0形成明确契约和边界用例。未命名账号不能都以空字符串撞上唯一索引；未命名与已锁定昵称使用可兼容的数据库表示。

数据库验收必须检查真实Workers SQLite中的外键、CHECK、条件唯一索引、0行条件更新和整笔回滚。`new_sqlite_classes`只代表平台存储类型，不代表业务建表完成。schema升级使用独立版本，不把平台migration标签当业务schema版本。

### 5.2 统一操作顺序

```text
验证HTTP入口与身份 → 受控RPC → 验证DO会话与请求归属
  → 查找并处理已有幂等结果/冲突
  → 准备必须在事务外完成的加密材料
  → 按最新服务端时间完成到期事件屏障
  → 同步事务重新核验身份、资格、版本和资源
  → 业务状态 + 事件 + 审计 + 通知 + 幂等结果原子提交
  → 提交后重排Alarm → 按接收者权限返回结果
```

`transactionSync`内部不得 `await`、外部请求或异步 `crypto.subtle`。异步准备完成后重新读取权威时间与最新状态，在最终事务前处理应优先发生的事件；不能拿加密前读到的目标状态直接提交。

已完成操作的重试在校验当前身份与归属后返回原结果，即使玩家随后已淘汰或阶段已改变，也不把已提交结果改成一次新拒绝。重放不会再次执行规则效果；新请求仍按当前门禁处理。

### 5.3 幂等与未知结果恢复

业务幂等键为 `(match_id, actor_id, request_id)`，同时绑定动作类型与稳定请求摘要。同ID同内容重放原结果，同ID不同内容返回 `409 REQUEST_ID_CONFLICT`。随机判罚、发行、扣额和通知均随同一业务事务落库。

当前前端跨刷新只保存请求标识和账号/场次，后端不能假定浏览器仍有原始秘密请求。M0确定并在M1落地以下协议：

1. `GET /api/operations/:requestId`区分完成、已受理处理中、暂未确认等状态；只查本账号本场请求。
2. 查询不到记录时不能宣布“未执行”，因为原请求可能仍在入口或异步准备途中。页面保持待确认，不自动产生第二个攻击ID。
3. 增加受保护的最终确认操作，例如 `POST /api/operations/:requestId/resolve`：同一DO内若已有结果则返回；若决定终止未提交操作，则原子写入取消屏障。迟到原请求必须在最终事务中检查该屏障，从而保证不会在用户重新行动后又悄悄生效。
4. 只有取得已完成结果或已持久化的取消结论后，前端才释放待确认状态。取消只适用于尚未提交的业务，不能撤销已生效攻击。
5. 对中途回收、待处理记录失去执行者等情况设定可核验的恢复规则；不把没有后续工作机制的 `pending`永久留给玩家轮询。

这是需要新增的恢复协议，当前代码尚未实现。取消确认接口本身须校验Origin/CSRF、账号、场次、幂等及并发；用延迟到达、回包丢失、重复查询和恢复后原请求继续执行的用例验证。

### 5.4 双时钟、事件屏障与Alarm

| 事项                                 | 权威时基                                                          |
| ------------------------------------ | ----------------------------------------------------------------- |
| T0、T1                               | 真实UTC                                                           |
| 阶段、15分钟重生、歌者、技术爆炸     | 有效比赛时间，暂停时冻结                                          |
| 错误攻击禁攻、180秒观战、UTC临时效果 | 真实UTC，比赛暂停时继续                                           |
| 历史生效、实际落库                   | 分别保存 `effective_game_ms/effective_utc_ms/committed_at_utc_ms` |

到期事件先按有效时刻排序；同刻阶段边界优先，然后重生期限，再歌者/技术爆炸及固定ID顺序，最后受理当前合法玩家行为。普通暂停前先补结算更早到期事件。

98分钟事件即使延迟被调用，也必须在原98:00对应UTC建立核验暂停，重新计算时钟并停在98:00，不能继续补到120分钟。核验暂停只由 `hunt-finalize`结束。

SQLite计划表是权威，单Alarm只负责唤醒。RPC与Alarm调用同一结算器；重排在事务外完成，使用持久 `scheduler_revision`复查异步排程是否覆盖了新计划。暂停后不调度尚未成熟的游戏时间任务，必要UTC任务仍可执行。

事件使用稳定ID、条件状态更新及通知去重实现一次效果。积压采用有限批次，未清理完应先继续结算并阻止越过屏障的新战局操作；失败事件记录诊断、维持受控拒绝并提供恢复路径，不能跳过失败事件。Alarm登记失败与业务事务失败分别记录，已提交的业务不能因排程失败被再次执行。

### 5.5 码本与加密

固定七色及位序，枚举350种合法配置。HMAC索引覆盖所有历史码，AES-GCM保存可授权恢复的配置，使用正确nonce、AAD和密钥版本；密钥、密文、原始索引不进入公开契约。

同场码HMAC规则和密钥版本必须固定；中途换HMAC密钥会令相同配置得到不同索引，可能绕过永久唯一性，不能作为普通“密钥轮换”直接执行。赛中如确需处理密钥事故，先暂停，制定保留全部已发行配置唯一性的迁移与复验方案。

领码重试返回同一份；退役、缺席、异常注销和未激活码都永久占用容量。20/10/0告警去重并只给授权裁判，耗尽后拒绝新发行并提示总裁判暂停处置，不代替裁判暗改重生资格。

## 6. 接口与前端联调方案

### 6.1 契约先行

为技术方案§15及前端已使用的路径建立端点清单：方法、角色/能力、请求Schema、响应DTO、时基、幂等、版本与测试。新增能力和旧接口扩展记录在公共契约及接口说明中。

| 登录与基础读取 | `/auth/exchange`、`/auth/session`、`/auth/logout`、`/public/site-config`、`/public/match` |
| 玩家           | nickname、self、本人消息/情报/历史、QQ模板及全部 `/action/*`                              |
| 恢复           | `/operations/:requestId`及受保护的最终确认协议                                            |

目击请求仍严格只有 `request_id/arm_a/arm_b`，多余字段拒绝。不能为了通用写入封装而给目击追加目标ID、场次、客户端时间或管理版本字段。

成功命中响应提供授权目标及情报；未命中仅提供统一文案、本人累计次数及实际处罚，内部分类和抽签值留在受限复核接口。已受理广播不透露母星匹配与歌者计划，光粒发射者不进入活人公共事件。

业务响应提供结构化结果和对应状态版本，页面不解析文案决定流程。错误统一包含稳定业务码、可读说明及必要的重试/最新版本信息；区分未登录、越权、格式、冲突、限速、阶段/资格改变和系统异常。`/api/*`所有错误返回JSON，禁止SPA回退的HTML假装接口成功。

### 6.2 一致快照与分页

建议新增按数据范围读取的聚合快照入口，由服务端完成鉴权后调用一次DO权威读取，返回同一 `revision/serverUtcMs`下的阶段、本人状态、动作和首屏数据。客户端请求的范围只是资源选择，不是自报角色；服务端逐项授权。

原有细分业务接口继续保留，长时间线、航次、通知和审计使用稳定游标分页。关键快照不得由前端任意拼装多个版本；若保留分段读取，须绑定同一读取版本并检测不一致后重取，不能只比较最外层比赛版本。

首期保留轮询，不先引入WebSocket。先按已有约2/3/5秒策略联调，再以24玩家、3裁判和大屏的真实请求量测并调整。只读无变化不递增业务版本；通知状态版本与战局预览涉及的实体版本分开管理，避免无关复制动作让所有管理预览不断过期。

### 6.3 投影与角色

服务端以字段白名单生成投影，禁止把整行数据库或完整 `payload_json`返回后让前端删除秘密。保留当前前端展示结构并通过适配器迁移，不能强行让数据库状态迎合模拟数据。

| 接收者                    | 可读范围与限制                                                                       |
| ------------------------- | ------------------------------------------------------------------------------------ |
| 未登录                    | 活动介绍和允许公开的最小阶段信息；不含秘密或全量参赛档案                             |
| 正常玩家、淘汰未满180秒者 | 本人状态/配置历史/情报、相应消息及公开事件；不含他人现役码和未公开母星               |
| 合格观战玩家              | 全部已发生战况，含光粒发射者、技术爆炸获得者、历史航次；每次重验淘汰、等待与撤销状态 |
| 大屏                      | 裁判会话下的观战范围投影，不含待发私聊、内部审计和未来计划                           |
| 完赛后的本场参赛者        | 完整已发生复盘，不受180秒等待限制；赛前已退出名单者不自动取得秘密复盘权限            |
| 裁判                      | 按职责返回审核、通知、事件或高级运维材料；完整随机审计和高风险修复仅给对应权限       |

三类裁判账号分别授权：通讯裁判侧重母星与通知，事件裁判侧重事件与通知，总裁判负责开赛、时钟、终局、纠错、换码、参数及高风险指令。前端 `permissions`只控制展示；操作级权限在DO中逐条检查，不能仅以菜单可见性或 `role='judge'`放行全部写入。

## 7. 玩法实施顺序与关键验收

### 7.1 母星、首航与T0/T1

实现昵称锁定 → 六位母星提交/递增版本 → 裁判核对版本与口令审核 → 离巢声明 → 手环材料确认进入staged → 锁定T0 → 本人领reserved码 → 确认ready → 锁定T1 → 全场原子激活。

`preflight-depart`与 `preflight-stage`采用已补充确认的两个业务步骤；第一次成功、第二次失败时可准确恢复中间状态。母星审核只有最新pending版本可通过，已审核坐标唯一；审核退回需原因。T0前不发码，T0不等于开赛，T1必须全员ready且数量一致，任一异常整笔回滚。

### 7.2 目击、处罚、重生与存活

按自码 → 当前有效目标 → 已退役码/可信竞速 → reserved/unknown等规则分类。4秒间隔和滚动60秒最多10次在查询码本前执行；重试不作为新目击计数。超过120次只告警，形成可追踪复核待办，不关闭目击资格。

同一现役航次仅一笔hit胜出；晚到旧码不罚。第一/二/三次失配按300秒、等概率淘汰或900秒、必定淘汰实现；第二次抽签只保存一次。失配次数与UTC禁攻跨重生保留，禁攻者仍能被击毁及开展其他合法行动。

统一处理击毁、退役、情报、通知、返航/淘汰；重生四步共用固定15分钟期限，且必须严格早于期限与65分钟。重生照片由本人声明已通过QQ发送，正常流程不新增逐次裁判审批。

抽取技术爆炸候选、统计存活人数、核算排名统一使用正式参赛身份与有效淘汰状态。第一阶段可合法重生的返航/准备/issued文明仍算存活，不能只数active便提前结束。

### 7.3 宇宙事件

广播只校验六位字符串、资格、次数和公开重复记录；条件插入、扣额、反向情报、独立歌者计划及通知同事务完成。匹配已毁但曾审核的母星仍授予反向情报，广播当下不鉴定真实性。

歌者自广播有效时刻起，每完整60秒独立5%首次清理，预抽计划严格早于65分钟。已被光粒摧毁的坐标也保留原清理事件，届时按无现存母星处理。

技术爆炸在锁定T1时依据正式人数固定 `M`与秘密时刻，8—55分钟分散排布；具体随机排布算法在实现中形成可复验约束。2人局按原公式为0次，24人局8次，不私自改成每种规模至少一次。到期按已确认候选范围均匀抽取，候选为空则结算为空事件，不补抽新时刻。

光粒成功发射即扣一枚，空坐标也消耗；母星毁灭不清空舰载库存，65分钟后库存只留历史、不能继续使用。所有母星毁灭调用同一事务内领域操作：active保留最后一命，未出航状态永久淘汰，重复摧毁不能重复生效。

### 7.4 阶段、终局与排名

65分钟批量毁灭母星并淘汰未出航者，同批淘汰共享并列组；90分钟关闭目击；98分钟自动暂停并等待总裁判整批资格裁决；普通resume不能绕过；裁决后至少两人存活才恢复22分钟狩猎；120分钟先完赛再拒绝同时刻攻击。

统一 `recordElimination`、`checkAutoFinish`和 `finalizeMatch`。批量淘汰全部完成后才检查0/1人提前完赛。排名遵循生存优先、幸存者按不同文明去重击毁数、淘汰者按生效UTC与并列组、竞赛排名跳号。无人存活不授冠军。

完赛先保存最终参赛资格及结果快照，再处理现役码退役和正赛计划取消；不能因为统一退役手环而误把冠军也设为已淘汰。赛后纠错生成新报告版本及更正说明，保留原始事件和审计。

## 8. 裁判管理、通知与安全

### 8.1 预览、执行与纠错

改变战局、资源、装备或配置的管理操作先预览，执行时绑定操作者、场次、动作、参数摘要、受影响实体版本和有效期。预览不能提前扣额、发码或选定随机对象；随机选择器预览展示候选范围，执行时再抽取并持久化。

执行前重新经过到期屏障、权限及状态核验；版本变化时要求重新核对。必要管理操作要求原因和总裁判权限。GUI与控制台共用服务，不存在绕过事务的“后台直接改字段”。

优先支持查询、时钟控制、UTC攻击静默、公告/私信、资源纠错、终局执裁、异常换码、攻击纠错、事件补结算和恢复诊断，再支持延迟公告与统计重播。命令解析使用注册式Schema和明确单位，不执行任意SQL、JavaScript或shell。重放公告不重结算原事件，管理公告不扣玩家广播额度或产生歌者。

异常换码在全场暂停中完成旧码永久退役、新码reserved、佩戴确认、激活和恢复；同色同款实物替换保持原码。攻击纠错联查航次、母星、码、失配、情报、淘汰、排名、观战和事件，不删除已发生的信息传播证据，不重抽既定判罚。

### 8.2 通知与账号引导

通知正文来自持久化记录，身份统一为“C07（归零者）”。`pending/copied/sent/error`独立保存，使用版本条件写入和源事件/收件人去重；复制成功、QQ已发送、规则已生效分别记录。失联和淘汰通知优先。

建立一次性的受限场次引导流程：先建schema，再用独立引导Secret与明确场次初始化名册和裁判凭证摘要。引导入口须校验环境、目标场次和初始化状态，首次成功后持久封闭；不提供覆盖已有比赛的一键初始化或重置能力。具体CLI与内部RPC装配在M0验证，preview首次使用在M1验收。

账号口令与会话令牌使用高熵随机值并只存安全摘要；会话到期、注销、凭证重置和裁判撤权均须生效。登录建立会话前使用严格Origin及JSON请求约束；建立会话后的写入使用Cookie、Origin与CSRF组合防护，不要求尚未建立的会话凭空提供CSRF令牌。

正式Cookie使用Secure、HttpOnly、SameSite及明确路径，不跨不必要的域共享。优先用本地HTTPS验证同源登录，完整Secure Cookie和QQ浏览器行为在preview再验收；本地临时兼容配置不能进入生产。

### 8.3 缓存、日志与恢复

私有API、观战、结果秘密复盘、裁判材料及错误响应设置恰当的 `private, no-store`，Functions自己设置安全响应头，不依赖只作用于静态文件的 `_headers`。查询参数、普通访问日志、错误栈和命令文本不得记录口令、会话Token、整套母星或手环秘密。

使用服务端Secrets和本地被忽略的 `.dev.vars`；`VITE_*`和contracts一律视为公开内容。请求大小、严格Schema、参数绑定、文本转义及登录/读取/写入限速均纳入测试。静态构建不带真实凭证；正式部署是否排除 `/dev-preview/`模拟入口在发布清单中明确，不能让模拟入口被误认成比赛服务。

PITR及导出按原方案建设，但必须演练回滚后的永久码本问题：恢复到早期书签会遗失后来已发且玩家可能看过的码。恢复前保全当前完整发行历史，恢复后将书签之后的发行记录合并为不可再发的历史占用，并核对事件、情报、通知、会话与Alarm。无法证明发行历史完整时保持暂停，由总裁判裁决，不能直接恢复发码。

代码回滚与数据恢复分别处理。优先使用兼容的向前迁移和审计化业务修复；整场PITR只在暂停、取证、评估并确认恢复方案后使用。导出与恢复材料不是另一份在线权威库，存入受限、加密且被Git忽略的位置。

### 10.3 真实负载与现场条件

使用24玩家、3裁判和大屏的实际轮询模型，测试平稳访问、T0集中领码、同时提交、通知积压及恢复网络后的集中刷新。记录端到端响应分位数、错误率、DO队列延迟、SQL读写和实际平台额度消耗；M0定出测量方法，M4依据排练与校园网络结果确认正式可接受阈值。

验证CSS/脚本等必要资产自托管，QQ内置浏览器能登录、刷新、切换QQ/高德后回到页面恢复，并能人工复制文本。校园Wi-Fi及移动、联通、电信直连分别验收，不能把本机代理访问成功当作校园可用性证明。

测试时钟加速验证规则，不替代真实云端Alarm演练。至少完成一次真实时间的完整赛程排练，关闭浏览器观察无人访问事件，并记录98分钟人工核验增加的墙上时间。

## 11. 部署和需要用户配合的时点

### 11.1 Preview发布流程

1. 本地完成该里程碑，运行格式/lint/类型、相关单元、Workers和端到端检查，确认实际测试数及失败项。
2. 读取实际Wrangler身份、资源、环境绑定与目标场次，检查只指向preview；需要重新登录时请用户完成浏览器授权。
3. 配置本轮所需preview Secrets，禁止在聊天、构建输出或仓库中披露值。发布Worker及迁移，再发布Pages dev分支。
4. 记录部署组合，执行真实HTTP/RPC、授权、持久化及该阶段专属云端验收。HTTP 200、静态页面可见或绑定connected都不能单独判为业务通过。
5. 提交可复核的结果和具体未通过项。后续开发继续回到本地。

Worker和Pages无法视为一次原子发布；接口变更采用可兼容过渡，迁移优先增量。回滚时核对两端版本和已有数据库schema，避免把旧Pages指向不兼容的新Worker，或旧Worker读取不可兼容的数据。

### 11.2 正式上线

完成M4和最终preview回归后，准备独立生产配置、Secrets、场次、名册和恢复材料；向用户报告实际验收结果与上线操作清单，再进入正式发布。用户当前的部署顺序要求纳入计划，本次仅编写文档，不执行发布。

先部署生产Worker与受控schema，再部署生产Pages，检查绑定与安全引导。正式子域名按原方案在Pages添加，阿里云新增对应CNAME并确认HTTPS，不默认修改nameserver。生产初始化不继承preview会话、随机安排、已发码或比赛进度。

在正式环境完成小范围预检及校园网络验收，保留Worker/Pages版本、数据库书签、配置摘要与账号发放记录。正式开赛前冻结发布；赛中不发布未经排练的代码或进行盲目数据回滚。
