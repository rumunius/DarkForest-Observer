# 裁判员指令系统完整规划

日期：2026-11-05。状态：目标设计，尚未实施。指令语言：`DF-Judge/1`。

本系统的定位是裁判完整控制台。裁判可以查询、筛选、随机选择、淘汰、恢复、发放资源、处理事件，并把这些操作编成批次、带参数的宏、条件指令或定时任务。管理指令不以维持参赛者之间的公平为限制：随机淘汰、定向奖励、批量处罚均是正式能力，不要求伪装成程序纠错。

同时，按用户最后补充，本轮以现有玩法与后端业务流程为基础，不建设跨阶段行动许可、无敌、额外生命属性、赛中动态改赛程或任意规则引擎；开赛准备仅允许按§5.2撤销或推迟尚未到达的T0/T1。65分钟后仍不能正式广播、发射光粒或进行普通重生；转场及终局核验的行动门禁不变。增强重点是让裁判能完整调用和组合管理能力，不重写玩家玩法。

**本文件是用户授权的裁判权限补充及完整语言规划。** 与核心文档中“只可纠错”或旧指令外观冲突的地方，裁判管理能力以本文件§2所列授权为准；普通玩家规则及未调整领域仍按原文和既有补充。两份核心文档保持原文。本文件不代表代码已经实现。

## 2. 完整系统的能力与边界

### 2.1 裁判拥有的管理权

| 管理领域   | 完整能力                                         | 与旧限制的区别                                     |
| ---------- | ------------------------------------------------ | -------------------------------------------------- |
| 生死       | 指定、筛选或随机淘汰；恢复参赛资格；批量处理     | 无需先证明程序误判，不禁止随机处分                 |
| 母星       | 第一阶段主动毁灭或恢复已登记母星；更正登记       | 主动干预不必建立纠错个案；不撤回别人已知的情报     |
| 资源       | 发放或收回现有光粒、技术升级、广播剩余额度       | 可以主动奖励，不限于补偿错误；沿用现有资源值域     |
| 处罚       | 调整个人禁攻截止及累计失配数；创建或撤销攻击静默 | 可主动赦免，不要求重新审判原攻击；保留原记录和抽签 |
| 目标       | 编号、集合、筛选、随机、标签、数值范围           | 强操作同样接受选择器，不强迫逐个抄编号             |
| 组合       | 批次、条件、带参数宏、定时任务、管理作业         | 不再只允许组合叙事消息；同一能力不因组合而消失     |
| 查询与消息 | 完整历史、任意支持的统计、批量私信、受控模板     | 支持筛选、时间窗口和统计发布，不限三个示例         |
| 管理手续   | 自动归档、可选个案、按实际影响确认               | 有操作记录即可，个案是整理工具，不是许可证明       |

“裁判拥有最高权力”体现在上述能力可用；系统仍须把裁判的决定准确落实成自洽状态。缺少新手环码、引用不存在、数据库写入失败属于无法完成的事实，不应报告成功。

### 2.2 明确保留的业务流程

- 身份及场次来自真实裁判会话。普通玩家、观察者和大屏不能执行管理命令。总裁判可使用全部赛事指令，其他裁判按授予职责使用；`execute as`只绑定目标，不替换操作者身份。
- 玩家行动仍受阶段、出航状态、暂停、终局核验及有效处罚共同约束。解除一项处罚不会解除其他限制；不增加跨阶段广播、光粒或普通重生。
- 八项赛前参数和正式名单在首次锁定T0后冻结；撤销或推迟T0不解除冻结。允许总裁判在原定T0或T1尚未到达时推迟或撤销该节点，具体按§5.2；不增加赛中改概率、改阶段边界或修改已到达T0/T1的能力。主动奖励通过管理事件记录，不改自然事件概率和计划。
- 350枚合法手环码在本场永久不复用；新出航、异常换码和资格恢复都用未发行码。需要换实物时保持暂停及现场核对，这是佩戴流程要求，不是维护公平的借口。
- 98分钟仍由独立核验批次一次结算资格、关闭核验暂停并决定开战或完赛。通用恢复不跳过该流程。
- 生死、母星、航次、码、资源、通知、观战权限及排名必须一起更新。原记录、原抽签及已传播信息保留；不通过删历史来冒充从未发生。
- 完赛后使用新战报版本更正，不重新开放比赛；活人不因裁判登录而得到观战、未来秘密计划或系统凭据。
- 网站不增加地图、GPS、距离选择器、轨迹、照片上传或QQ自动发送。原生数据库恢复继续使用独立部署管理员流程。

### 2.3 本轮明确不建设的三项

1. 人工执裁后的离线攻击/比赛过程补录语言。
2. 中止、作废或强制结束比赛的命令及相应新结算状态。
3. 撤销、推迟或重设已经到达的T0/T1；尚未到达的已锁定节点按§5.2允许推迟和撤销，不允许直接提前。

宏、定时、批量和任意字段修改均不能间接实现这三项。本轮也不增加无敌、伤害倍率、独立生命数、跨阶段能力开关、持续暂缓自动完赛或自由改写时钟的系统。

## 3. 操作体验、权限与执行协议

### 3.1 控制台与权限

控制台提供命令树、中文帮助、参数/选择器补全、输入错误定位、目标预览、确认、结果、关联记录和可检索历史。电脑支持多行命令块，手机保留完整能力和常用表单。GUI可显示对应规范命令，但不要求常用操作必须输入文本。

| 代号 | 能力                                                   | 默认岗位         |
| ---- | ------------------------------------------------------ | ---------------- |
| Q    | 职责内查询，敏感字段按具体权限返回                     | 全体裁判         |
| C    | 母星审核、通知、消息、标签                             | 通讯裁判、总裁判 |
| E    | 事件查询、统计、消息、临时静默                         | 事件裁判、总裁判 |
| H    | 全部赛事管理、随机处分、主动奖励、纠错、组合与任务授权 | 总裁判           |
| A    | 账号、设置、导出、恢复核对                             | 总裁判的系统职责 |

组合权限等于实际展开操作所需权限的并集。不能通过宏名、选择器、来源字段或定时任务冒充总裁判；总裁判使用合法业务命令也不需要额外的“公平例外”许可。

### 3.2 预览与确认

影响生死、资源、处罚、母星、事件、时钟、账号或信息公开的指令先生成服务端预览，确认后执行。查询直接返回；标签、现场备注、草稿编辑、个案整理和宏定义等不改变正式战局的操作直接保存并记录，可以显式请求预览。通知复制/发送沿用现有独立版本及真实确认，不另建一层PLAN手续。

```text
/player eliminate @random[alive] --reason "裁判安排随机淘汰事件"
  → 显示候选、抽取规则、可能影响及提前完赛风险，不先抽人
/confirm PLAN-42
  → 抽取一次，完成淘汰并返回真正目标
```

`/plan /<操作>`可显式预览任何写命令。个案编号通过可选的`--case`关联，未填写时系统直接生成操作档案，不要求先创建CASE。正式操作原因可直接输入，也可由GUI/宏继承；没有人工说明时记录“裁判主动干预”及具体命令、操作者，不为了凑一段理由挡住命令。

预览显示目标、前后状态、新码消耗、处罚和期限、观战、通知、信息公开及可能提前完赛。随机预览只展示候选与可能影响，真正目标在执行时选一次；重试不会换人。

预览检查的是**本操作实际依赖的状态**：目标航次、待改资源、阶段、候选、所选原记录、权限及必要人数。其他无关玩家行动不自动使预览作废。实现可用现有revision快速发现变化，再重读并比较依赖，避免给每张表全面新增版本字段。

只要依赖和权限仍相同，预览不因“已经看了60秒”而作废；服务端可按存储策略清理旧预览，清理后的计划重新生成。T0/T1、阶段越界、候选或有关人数变化必须重新核对；不能自动把新目标当作已经确认过。

### 3.3 执行、批量和提前完赛

正常顺序为：解析 → 鉴权 → 查询已有请求 → 到期事件补结算 → 解析目标/条件 → 验证预览依赖 → 同步业务事务 → 同事务写业务、日志、通知及结果 → 提交后安排下一Alarm。

- 同一请求ID同一规范内容重放原结果，不重复发码、抽人、发放、处罚或通知；同ID不同内容拒绝。一个PLAN只能消费一次。
- 确认丢包先查原操作结果，不能新建请求猜测性重做。结果为已提交、确定未提交或待确认，不能把超时显示成执行失败。
- 编号及选择器集合去重。同一命令默认按编号稳定处理；随机选人使用安全随机数无放回抽取。
- 默认批次在一笔事务中完整提交；先校验全部步骤和所需码源，任一步失败全部回滚，不允许做一半却报整批成功。
- 生死批次在全部步骤完成后检查一次提前完赛。不得逐个淘汰时提前截断整组；也不新增跨请求的“暂停自动完赛”开关。已经完赛不能通过另一个请求复活；如需同一次干预先淘汰再恢复，应放在可执行的同一批次中，预览显示最终人数。
- 大操作可以显式选择`--mode sequential`建立可追踪作业，每步独立提交、记录进度与失败位置；不得无声地把原子批次改成部分成功。逐步作业每步仍按正常规则检查完赛，一旦比赛结束后续正赛步骤停止。

### 3.4 故障读取与恢复性操作

原有事件持续失败时，普通比赛写入继续阻断；裁判仍可读取已提交状态、真实计划及故障。总裁判可故障暂停、处置阻塞事件、重试或重排Alarm。结果说明未结算范围和截至版本。

这是恢复可靠结算的通道，不是跳过失败事件继续比赛的通道。故障暂停以成功提交时刻生效，不能回填更早暂停。重排Alarm不清除失败事实；恢复前仍须处理积压。

## 4. Minecraft风格选择器与条件

### 4.1 目标及筛选

| 写法               | 含义                                                               |
| ------------------ | ------------------------------------------------------------------ |
| `C07`、`{C07,C12}` | 指定文明或显式集合                                                 |
| `@a`               | 当前正式名单，含存活和已淘汰者，不含未选入或赛前退出者             |
| `@alive`、`@dead`  | 正式开赛后的未永久淘汰者、永久淘汰者；合法返航/重生准备仍属于alive |
| `@random[alive]`   | 存活文明中均匀抽一名；裸@random从@a抽一名                          |
| `@pool`            | 本场预注册玩家账号池，用于赛前名单、账号及标签等适用操作           |
| `@s`               | execute as中绑定的当前文明，权限仍来自真正操作者                   |

```text
@a[status=returning]
@alive[homeworld=alive,tag=reward]
@a[scores={wrong=1..2,photons=0},tag=!contacted]
@alive[sort=random,limit=3]
```

筛选支持status、homeworld、tech、tag、scores、sort、limit。status使用现有飞船状态；homeworld为alive/destroyed/pending；scores提供photons、broadcasts（剩余）、wrong、kills（去重有效目击）。数值范围支持`2`、`1..3`、`..2`、`2..`，上下界包含。默认按ID排序；random无放回；limit按本场实际集合大小截取，不另设350目标的语言上限。

逗号表示且，`!`否定一个值；支持重复tag要求多个标签，不静默覆盖重复单值项。需要“或”或更复杂组合时使用下面的布尔条件。`@random`是固定抽一人的简写，多人随机用sort=random和limit。无匹配目标的查询返回空列表，写入返回明确的“0人，无变化”，不当作系统故障。

**淘汰、恢复、发放、换码、资源和处罚管理同样支持选择器。** 随机淘汰无特殊禁令；预览展示候选、数量和抽法即可。随机无回放重抽，选择器不跨场，不接收昵称模糊猜人。不支持依赖网站地图的distance/x/y/z等空间参数。

### 4.2 条件与当前对象

```text
/execute as @a if (player @s status returning or player @s status preparing) run { tell @s "请查看本人返航进度。" }
/execute if match phase forest unless match paused true run { tech grant @alive[sort=random,limit=2] }
```

支持if、unless、and、or、not和括号；not优先于and，and优先于or。连续if/unless仍表示且。条件包括实体存在、阶段、暂停、存活人数、玩家状态/母星状态、资源范围、效果是否有效、事件状态和标签。

`as`逐人绑定@s；没有as也可执行全局条件。顶层as目标在开始时确定，步骤内部选择器按该步骤的工作状态解析。原子批次中的后一步能看到前一步更改；正式开始前用同样顺序生成完整影响预览。

嵌套条件、批次和宏可互相调用，不需要把它们写成任意代码。调用深度和执行预算防止资源耗尽；宏调用图不允许直接或间接递归。条件为假记为无操作，保留判断版本，不生成空消息。

## 5. 完整指令目录

本目录为规范路径。参数中的`<目标>`默认支持编号、集合、筛选和随机；只有本质上需要唯一对象的查询/版本审核标明`<单目标>`，多目标可用execute逐个调用。所有写指令可附`--reason`、`--source`、`--case`；选项顺序自由，具体说明见§7。

### 5.1 帮助、预览与历史

| 指令                                                                   | 权限     | 功能                                         |
| ---------------------------------------------------------------------- | -------- | -------------------------------------------- |
| `/help ["命令路径"]`、`/version`                                       | Q        | 自动生成帮助、参数、例子、语言与实际实现版本 |
| `/whoami`、`/capability list`                                          | Q        | 操作者、场次、能力；不返回凭据               |
| `/selector inspect <目标>`                                             | Q        | 确定性名单或随机候选说明，查询不抽人         |
| `/plan /<写操作>`、`/plan inspect <PLAN-ID>`、`/plan cancel <PLAN-ID>` | 对应权限 | 显式预览、查看或关闭未执行计划               |
| `/confirm <PLAN-ID>`、`/request inspect <REQ-ID>`                      | 对应权限 | 确认及查询原结果                             |
| `/command history`、`/audit list`、`/audit inspect <AUD-ID>`           | Q/A      | 独立命令历史及关联业务提交证据               |

列表支持--limit、--before、--format以及适用的--target、--actor、--kind、--status、--since、--until、--search。筛选在服务端全量历史上执行，不只查已加载100条。非列表不能使用无意义的分页选项。

### 5.2 名单、审核与统一开赛

| 指令                                                                           | 权限 | 功能及现有前置条件                                                |
| ------------------------------------------------------------------------------ | ---- | ----------------------------------------------------------------- |
| `/match status`、`/roster list`、`/preflight list`                             | Q    | 阶段、名单、人数、准备缺项及T0/T1                                 |

| `/homeworld verify <单目标> version <整数> code <六位串>`                      | C    | QQ核对后的最新版审核，重复口令及旧版本拒绝                        |

| `/match postpone-release at <绝对时间>`、`/match postpone-start at <绝对时间>` | H    | 原节点尚未到达时推迟T0/T1，新时刻必须严格晚于当前锁定时刻         |
| `/match cancel-release`、`/match cancel-start`                                 | H    | 原节点尚未到达时撤销T0/T1倒计时，保留准备事实及历史，等待重新锁定 |

**锁定与变更规则：** T0/T1均由总裁判手动锁定未来绝对时间，全员审核或就绪不会自动安排。推迟和撤销同样先预览再确认；预览绑定节点、当前锁定时刻及排程版本，显示准备状态、关联任务和通知变化。确认执行时须满足服务器权威UTC严格早于原锁定时刻，且节点尚未结算；等于或晚于原时刻即拒绝，不因Alarm延迟或阶段字段尚未更新而放行。到期事件先于同刻管理命令，宏、批次及定时执行也不能绕过该边界。推迟要求新时刻严格晚于原时刻，不能用于提前节点。

撤销T0后保持`armed`并清空当前`release_at`，表示“发码安排已撤销，等待重新锁定”，不回到`setup`；本人不能领码，原staged事实保留。首次锁定T0形成的名单、参数和母星登记冻结继续有效，已有缺席/退出流程保留但不得补新人。`arm-release`可在该等待状态重新设置未来T0，重新核对全部首航准备条件。撤销T1后从`start_countdown`返回`outfitting`并清空当前`started_at`，保留reserved码、有效穿戴确认及T0发行事实；可按既有流程处理缺席/退出，再由`arm-start`重新核对全员ready/reserved并锁定未来T1。旧锁定时刻及每次变更均保存在审计中。重新锁定是新的明确开赛授权，不是对已撤销节点执行提前操作。

仅推迟T1或撤销后按同一正式名单重新锁定T1时，保留原技术爆炸次数及秘密游戏时刻，不重抽。撤销T1期间其派生游戏事件保持待重新锁定、不可执行；重新锁定后复用原计划。若期间按既有退出流程改变正式名单，重新锁定预览必须明确展示人数、次数及计划修订；确认后按最终人数生成新版本计划，旧版标为被替代并保全，禁止两版同时执行。65/90/98/120分钟仍保持原游戏时刻，只随实际T1映射到UTC，不改阶段时长。普通UTC任务不自动顺延，game任务不在开赛前执行；关联任务在预览中列出，必要的修改另行明确授权。

节点字段、阶段、有效计划及新通知在同一同步事务中更新，旧排程留档且不得再次执行，相关旧预览失效；同一请求重试返回原结果。提交后按最新scheduler_revision重排Alarm，旧Alarm唤醒重新读取有效计划，不依赖删除闹钟保证正确性。重排失败区分“变更已提交、调度待恢复”，不能报告未提交并诱导重复执行。每次变更生成替代公告；未发送旧通知标明被替代，已复制/已发送事实保留并提示人工更正QQ公告，不冒充已经撤回。

不提供跳过首航准备、提前激活、修改已到达T0/T1或赛中增补正式名单。T0已到达后继续准备并安排T1；T1已到达后需要延后进程时走暂停/恢复，不移动比赛起点。这里只保留统一开赛所依赖的流程，不以此限制赛中随机处分和主动奖励。

**资源值域按本轮“小幅扩展现有后端”的要求保留：** tech-level为0/1、photons为0/1、broadcasts为剩余0—2。不建设多弹药库存、无限资源哨兵值或多级科技。这些范围来自现有玩法表示，不是规定裁判整场只能发一次：光粒用掉后可反复补，广播用掉后可反复补回两次。补广播不删除已经广播过的坐标，同坐标不重复广播的业务规则保留。

**恢复资格沿用现有状态机：** 操作涉及新配置和现场佩戴时保持全场暂停；撤销当前有效淘汰、立即撤销赛中观战、处理旧超时任务、退役旧码并在需要时发新保留码，裁判核对后code activate。第一阶段可将任何来源的淘汰恢复为当前仍合法的准备/待激活状态；母星已毁且需要恢复飞船时，可按现有人工恢复最后一命的方式签发待激活码。后续阶段同样恢复为待激活最后一命，不恢复母星、不开放普通重生、不重设阶段。

这需要给现有管理恢复函数增加“裁判主动恢复”入口，免除“必须是人工误淘汰”的证据判断；不能直接用一个status赋值省掉码、权限、任务及淘汰记录联动。已有后续航次或独立有效事实不能自动处理时列出冲突，允许裁判通过对应业务操作整理后再恢复。完赛后的新请求仍不重开比赛。

## 6. 组合与任务的精确行为

### 6.1 保存授权、目标和版本

schedule默认`--targets live`：到期按原选择器解析；可选snapshot保存创建时的候选范围，到期在原范围中复核资格，不从外补人。随机只在真正执行时抽一次，结果和业务提交一起保存；原子批次回滚后无成功结果，重试沿同一请求处理。

宏参数支持target/int/duration/text/bool，仅以类型化值替换对应参数槽，不作为代码字符串重新解析。`$who`用于参数槽，消息`${id}`等属于注册文本字段，两者不混用。宏内部可调用其他固定版本宏，定义时检查循环，执行时再次确认展开版本。

target型参数在每次宏调用开始时解析一次，本次调用中所有引用复用同一个集合；传入随机选择器时也只选一次，避免“奖励一个随机人、通知另一个随机人”。参数候选在预览中说明，实际绑定在提交时保存。宏正文里另写的独立选择器按步骤解析，作用不同，帮助须举例说明。

确认一个含强操作的宏/任务，就是确认其完整业务影响与执行条件；不在每个子步骤要求裁判再次在线点确认。目标是live或随机时，预览清楚写明候选规则、最多人数及可能的生死/完赛后果。

### 6.2 定时、迟到和完赛

任务与AST保存到单场DO并复用scheduled_events/Alarm，不使用浏览器倒计时。UTC任务在一般暂停期间仍成熟，game任务随有效时钟冻结；同一时刻先执行既有阶段边界、重生超时和宇宙事件，再执行管理任务，稳定ID排序。

提供`--late run|skip|review`和可选`--max-lateness <时长>`。普通消息默认run，迟到标出原计划与实际发送时间；生死/资源/事件干预默认review，迟到进入“待重新确认”，防止把计划中的动作挪到另一个局面；裁判可在创建时明确选run，授权迟到后按当时状态执行，不固定“五分钟就丢弃”。skip明确记录跳过原因。

静默若选择迟到run，以实际生效时刻开始完整指定时长；若裁判要严格在原时间段生效，可设`--end-at <绝对时间>`，到期后不补足。两种语义显示清楚，不隐式选一种。

完赛自动取消会改变正赛的任务；普通集合/事务通知可在创建时设`--after-end keep`，完赛后继续，默认消息keep、战局操作cancel。混合任务按展开步骤分类，不允许用keep执行赛后生死/资源干预。恢复锁下不执行任务；恢复后按原定迟到策略处理，不偷偷重启倒计时。

到期检查创建者仍启用且仍有相应业务权限，失权不借系统身份继续；密码重置不自动作废仍有效的业务授权。任务取消与执行使用条件更新互斥，取消已完成任务只返回原结果，不删除发生事实。

### 6.3 历史、信息与修复

文明历史、命令历史、真实计划、已发生事件、业务审计五者分开，按稳定水位和游标分页，每页重新鉴权。控制台读取按裁判职责返回；观战及赛后复盘继续走原有读接口。未来随机安排、私人材料和凭据不进入观战或普通公开响应。

原始命令可能含秘密，受限日志加密保存原文、普通历史脱敏；查询日志保存条件、字段投影、水位及数量，不复制完整秘密正文。预览、拒绝、成功、无操作及任务子执行状态分别记录，不能把生成任务写成效果已生效。

恢复、换码、攻击修复均调用领域操作，同时处理码、航次、淘汰、期限、通知、战绩和观战。已有后续事实无法可靠组合时返回具体关联记录供裁判选择下一操作；不只说“不公平”，也不直接删除后续记录。主动裁决与纠错分别记来源，裁判不必谎称系统出错才能改变当前状态。

### 6.4 保留的数值限制

| 限制                 | 本规划的选择与理由                                                                                             |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| 本场码容量与资源值域 | 350合法码不复用；科技0/1、光粒0/1、广播剩余0—2，复用当前数据和玩家业务                                         |
| 概率与整数           | 概率0—100，整数在JavaScript安全整数内且最终数据库字段合法；无溢出、负库存或无意义概率                          |

| 嵌套深度             | 最多32层，拒绝递归宏，防止调用栈和循环耗尽；正常复杂组合仍可表达                                               |

## 7. 形式化语法

### 7.1 词法、选项和类型

以下为ISO风格EBNF：`=`定义，`,`连接，`|`选择，方括号可选，花括号重复，分号结束，`? ... ?`为词法类别。文法描述先规范化后的命令；**用户输入的选项顺序自由**，解析器识别本层选项、保留参数类型后移到规范尾部，不能按字符串替换处理。嵌套块中的选项归所属语句，外层原因/来源/个案可继承，内层显式值覆盖。

输入允许空格、tab和多行；块内用分号或换行分隔语句，允许末尾分隔符，规范化后统一为分号。字符串使用JSON双引号和转义，多行编辑器的文本内容由编辑器正确编码，字符串中的斜杠/花括号不作代码。命令关键字小写，文明ID和颜色ID保持现有大写；全角符号可在编辑器明确提示转换，不在服务器偷偷猜测。

绝对时间接受带时区的RFC3339字符串，例如`"2026-11-05T15:15:00+08:00"`或`"2026-11-05T07:15:00Z"`，统一存UTC。缺失时区时要求补全，避免按服务器时区猜测。时长支持`90s`、`1m30s`、`1.5m`，转换到整数毫秒；裸90不自动猜单位。游戏时刻使用`g98:00`或`g12:30.250`，秒00—59。

不要求裁判换算成Z结尾UTC：北京时间可直接写`+08:00`，预览同时显示北京时间、时区及距执行的剩余时长。`utc`表示绝对真实时间这一时基，不要求输入采用UTC零偏移。当前不定义`"15:30"`、无时区日期或“今天下午三点半”等简写；相对预约可用`schedule create utc in 1m30s`，推迟T0/T1命令则明确给出新的绝对时刻。

规范化只改变表示，不改变决定：同请求ID的摘要基于固定语言版本及规范AST；`1m30s`和`90s`规范为同一时长，宏确认绑定具体版本。六位坐标按字符串保留前导零。未知选项、重复互斥选项、不适用选项和多余参数明确报错，不执行“最接近”的指令。

### 7.3 文法之外的必要校验

文法描述能写出的结构，注册表再校验：命令是否实际支持、选项属于哪类操作、目标单复数、宏参数类型、ID归属和存在性、字段读取权限、阶段与现场条件、资源值域及预算。条件中的player/score/tag按单个绑定对象求值；需要集合判断时用entity或execute as，不对多人隐式选第一个。

stats事件类别使用已注册业务类别，如sighting-hit、broadcast、homeworld-destroyed、elimination；不接受表名或SQL片段。显示failed的计划状态可由既有pending状态与诊断字段计算，不要求改原事件状态存储枚举。字符串中的`${...}`只识别注册文本字段；`$参数`只能填入声明的参数槽，不变成新命令名或关键字。

## 8. 典型操作示例

以下均为设计示例，不是执行记录。影响战局的命令会返回PLAN-ID，随后确认；示例中的ID由实际前序操作返回。需要暂停/现场核对的命令必须满足真实条件，定时和批量不会补造这些事实。

### 8.1 随机淘汰与批量处分

```text
/selector inspect @alive[sort=random,limit=3]
/player eliminate @alive[sort=random,limit=3] --reason "裁判安排随机淘汰事件"
/confirm PLAN-random
/player eliminate @alive[tag=penalty] --reason "处理已标记的文明"
/confirm PLAN-eliminate
```

预览不先选中中奖/淘汰者；确认抽取一次。随机淘汰可能导致提前完赛，预览必须说明。原因默认可用judge_intervention，不强迫选择虚假的违规原因。

### 8.2 主动奖励与事件

```text
/photon grant C07 --reason "补给一枚光粒"
/confirm PLAN-photon
/tech grant @alive[tag=reward] --reason "奖励所选文明"
/confirm PLAN-tech
/event trigger tech-burst --reason "额外进行一次随机技术爆炸"
/confirm PLAN-random-tech
/event trigger tech-burst C12 --reason "指定奖励C12"
/confirm PLAN-target-tech
/event trigger singer 001234 --reason "裁判主动清理"
/confirm PLAN-singer
```

第一阶段即可执行，不为此暂停全场。相同光粒库存不叠加，但用掉可以再补。母星已毁的正常出航者可获得主动奖励；自然抽奖候选不因此被修改。65分钟后的新发放请求不开放光粒或广播。

### 8.3 赦免处罚与群体私信

```text
/penalty clear @a[tag=pardon] --reason "裁判解除个人禁攻"
/confirm PLAN-pardon
/penalty wrong-set C07 0 --reason "重置C07的累计失配"
/confirm PLAN-wrong
/tell @a[status=returning] "${id}（${nickname}），请核对本人返航进度。"
/confirm PLAN-tell
/effect create attack-silence @a for until-revoked --reason "持续静默至裁判解除"
/confirm PLAN-silence
```

原攻击和抽签保留。清个人禁攻后若仍在转场或静默中，仍不能攻击。静默不冻结比赛时间。

### 8.4 带参数宏、条件及嵌套组合

```text
/macro define "奖励提醒" params (who:target,note:text) run { tech grant $who; tell $who $note; }
/macro run "奖励提醒" (@alive[tag=reward],"请查看个人资源。")
/confirm PLAN-macro
/execute as @a if (player @s status returning or player @s status preparing) run { tag add @s "需联系"; tell @s "请核对返航步骤。"; }
/confirm PLAN-condition
/batch run { penalty clear C07; resource set C07 broadcasts 2; tell C07 "裁判已处理。"; } --reason "一次处理完成"
/confirm PLAN-batch
```

宏定义直接保存，run确认绑定当时的宏版本。参数只替换对应类型槽，不把文本作为脚本运行。混合直接保存项与战局操作的组合按较高影响统一预览确认。

### 8.5 定时随机事件与迟到策略

尚未到达原节点时，可先预览并确认开赛安排变更（以下时间须满足§5.2的未来及严格推迟条件）：

```text
/match postpone-release at "2026-11-05T15:30:00+08:00"
/confirm PLAN-postpone-release
/match cancel-release
/confirm PLAN-cancel-release
/match arm-release at "2026-11-05T15:35:00+08:00"
/confirm PLAN-arm-release
```

T1对应使用`postpone-start`、`cancel-start`及`arm-start`，同样逐次预览确认。撤销后保留冻结与准备事实，重新锁定重新核对全员；原节点已经到达时不能执行撤销或推迟。

```text
/schedule create game at g40:00 run { player eliminate @random[alive]; } --late review --reason "40分钟随机干预，迟到再问裁判"
/confirm PLAN-delay-kill
/schedule create utc in 1m30s run { tech grant @alive[sort=random,limit=2]; } --targets live --late run --reason "授权到期主动奖励"
/confirm PLAN-delay-reward
/schedule create utc at "2026-11-05T16:30:00+08:00" run { announce @a "请返回中控室集合。"; } --after-end keep
/confirm PLAN-gather
```

创建时刻必须使绝对执行时间尚在未来；固定game时刻须尚未经过。到期仍检查第一阶段等既有条件，晚于65分钟的奖励不会因预先授权而放行。集合通知可以赛后保留，改变战局的任务不能借keep越过完赛。

### 8.6 主动恢复与装备核对

```text
/clock pause --reason "准备恢复文明并核对新配置"
/confirm PLAN-pause
/player restore @dead[tag=return-to-game] --reason "裁判决定恢复所选文明"
/confirm PLAN-restore
/inspect C07
/code activate C07 issue ISS-new --reason "已核对新配置佩戴"
/confirm PLAN-activate
/clock resume --reason "核对完成"
/confirm PLAN-resume
```

恢复不要求此前判罚错误，旧码不复用，观战立即撤销。后续阶段只恢复待激活飞船，不恢复母星或普通重生；仍处于hunt_review时最后一条resume不会代替hunt finalize。

### 8.7 终局、历史与统计

```text
/hunt draft create
/hunt draft set HD-cutoff {C07,C12} outside_at_cutoff
/hunt draft inspect HD-cutoff
/hunt finalize HD-cutoff --reason "完整资格名单已核对"
/confirm PLAN-finalize
/history C07 kind attack --limit 30 --format json
/attack list --target C07 --since g10:00 --until g20:00
/stats count @a[status=returning]
/stats events sighting-hit window 5m
/reveal @a run { stats events sighting-hit window 5m }
/confirm PLAN-stats
```

草稿编辑不逐次要求PLAN；finalize整体确认后一次结算，同组并列。真实位置裁决须由裁判负责；想单纯随机淘汰应使用player eliminate，不造假位置证据。stats只查询，reveal才发布。

### 8.8 原事件重试与简化手续

```text
/event inspect EVT-blocked
/event retry EVT-blocked --reason "故障已修复，按原计划补结算"
/confirm PLAN-retry
/code reissue C07 --reason "现役配置损坏，需要换码"
/confirm PLAN-reissue
/player rename C12 "新昵称" --reason "更正登记"
/confirm PLAN-rename
```

换码仍须暂停和核对；不需要先建CASE。可以事后建立个案并关联这些操作，但个案不决定权限。原事件retry不变成新的随机抽奖。

## 9. 实现结构、协议与工作范围

### 9.1 优先复用现有业务

注册表是命令路径、Schema、中文帮助、权限、读写类别、目标基数、预览、处理器及组合能力的唯一清单。Lexer/Parser只生成带位置的AST，选择器与条件生成目标和执行计划，Executor调用现有judge/life/纠错/scheduler/通知服务，不接受SQL/脚本文本。

GUI、HTTP、命令、宏和定时任务调用同一业务。总裁判权限只在真实认证后用于管理入口，不能给玩家会话加绕过标志。字段修正不代替领域流程，尤其淘汰、恢复、换码不能只改flights.status。

| 工作层     | 本轮需要的变化                                                                            | 不延伸的范围                                |
| ---------- | ----------------------------------------------------------------------------------------- | ------------------------------------------- |
| 控制台语言 | 注册式解析、选择器、布尔条件、参数宏、嵌套块、选项和帮助                                  | 不做通用脚本解释器                          |
| 管理入口   | 多目标适配、主动恢复/奖励来源、个人处罚管理、自动操作档案                                 | 不改变玩家阶段判断，不新增能力覆盖系统      |
| 原子批次   | 抽取可复用同步业务步骤，由外层一次事务及最终autoFinish处理                                | 不加持久暂缓自动完赛或重开接口              |
| 资源       | 现有0/1光粒及0—2剩余广播调整、联动科技                                                    | 不增加库存等级、无限值和新行动类型          |
| 任务       | scheduled_events管理任务负载、创建者授权、目标/迟到/赛后策略；未到达T0/T1的专用撤销与推迟 | 不改自然事件概率、阶段游戏时刻或已到达T0/T1 |
| 预览       | 基于真实业务读取比较依赖，减少无关revision冲突                                            | 不要求全面事件溯源或为每行新建版本          |
| 历史       | 命令、业务、计划及审计独立查询，稳定分页和过滤                                            | 不建设任意历史快照引擎                      |

现有管理服务需要局部扩展，不应声称完全零改动。比如目前恢复入口检查暂停及原淘汰来源；主动恢复需要保留暂停/码/任务联动，新增管理来源分支，去掉“仅误淘汰”判断。批次需要把现有每次自动完赛检查集中到整批末尾。这些是管理服务复用改造，实施时检查调用范围并验证；不把“尽量复用”当作无需验证的保证。

原子块只对同一DO内的同步业务变更承诺全部提交。Alarm重排、导出等异步步骤使用提交后工作记录，不能在SQLite事务里await，也不能声称数据库回滚会撤回已发生的外部动作。包含这类步骤时，预览区分“业务已提交”与“后续任务待完成”，复用现有调度/导出机制；无法按此表达的操作明确要求逐步作业，而不是基于影响公平设禁令。

### 9.2 请求与执行结果

```json
{
  "request_id": "REQ-example",
  "language_version": "DF-Judge/1",
  "command": "/confirm PLAN-example",
  "preview_token": "opaque-server-token"
}
```

身份、场次及当前时间来自服务器。预览绑定AST、权限、相关业务依赖、随机候选和影响摘要；确认不能换参数。已有全局expected_revision可用于变化提示，是否需要重确认以相关依赖比较为准，不能为了兼容旧字段继续拒绝无关变化。

结果至少包含command_id、request_id、父命令/任务、状态、中文说明、实际目标、创建ID、关联审计、有效比赛时刻、生效UTC、实际提交UTC及业务影响。状态区分queried/previewed/committed/no_op/rejected/pending/skipped/review_required；逐步作业另有已完成/总数/失败位置，不能混成整批成功。

### 9.3 数据与保全

保留现有request_journal、audit_logs、业务事件和通知履历；新增命令原文受限日志、预览、标签、宏不可变版本、核验草稿及作业记录。可选个案仅整理引用。管理任务复用scheduled_events，不建立第二套比赛状态。

已确认任务保存操作者、需要的权限、AST/语言版本、宏展开版本、目标策略、原时间、迟到/赛后策略、来源及已确定结果。备份恢复保全这些记录及发行/传播事实，恢复后未消费预览失效、旧会话撤销，待办按原策略核对。

### 9.4 错误与说明

错误给出具体参数位置、目标、当前状态和可执行下一步。主要类别包括语法/类型错误、越权、相关依赖变化、请求ID冲突、目标状态冲突、需暂停/穿戴核对、阶段不适用、事件阻塞、码源耗尽、执行预算不足及任务待确认。

空选择、重复设置、条件为假、对已持有光粒者grant均是清楚的无变化结果，不当作运行崩溃。不能用“影响公平”拒绝已授权的随机淘汰、定向奖励或处罚赦免；拒绝必须对应本文件保留的业务条件或真实技术失败。

## 10. 实施顺序与验收

### 10.1 交付顺序

1. 注册表、解析、类型、权限、帮助、实际能力返回、日志及相关依赖预览。
2. 完整映射现有查询、时钟、名单、审核、终局、通知、装备、账号、结果和恢复核对。
3. 完成主动生死/母星/资源/处罚管理、多目标和随机选择；既有后端只补必要管理分支。
4. 批次统一提交和最终完赛检查、布尔条件、带参数宏、嵌套组合及可追踪逐步作业。
5. 定时任务授权、目标、迟到、取消、赛后通知、历史和恢复保全。

以上是施工顺序，全部完成且验收后才能称完整指令系统；不能把当前简单解析子集称为已经完成本规划。

## 附录A：本轮设计选择与理由

本附录记录按用户“自行决定并供审阅”的要求作出的选择，取代旧版把裁判能力收窄为纠错工具的决定。

| 编号 | 选择                                                            | 理由及边界                                                   |
| ---- | --------------------------------------------------------------- | ------------------------------------------------------------ |
| A01  | 随机淘汰、筛选处分、主动奖励和恢复都是正式能力                  | 不再以公平为由删除裁判权力                                   |
| A02  | 不增加跨阶段行动、无敌、多生命或动态规则系统                    | 遵从用户最后补充，避免大幅改变玩家业务                       |
| A03  | 三项排除能力仍含已到达T0/T1修改；未到达可撤销或推迟，赛后不重开 | 不回退生效节点；未到达节点走专用排程修订，冻结与发行事实保留 |
| A04  | 个案可选，系统自动生成操作档案                                  | 原因、前后状态和操作者足以形成基本证据，不强迫先办手续       |
| A05  | 战局操作预览确认；分类/草稿等直接保存                           | 保留真实影响核对，减少无关反复确认                           |
| A06  | 比较相关依赖，不硬性60秒及全局revision作废                      | 无关行动不应打断裁判，阶段和目标变化仍要看清                 |
| A07  | 所有适用命令接受选择器，随机强操作无禁令                        | 真正统一目标模型；单对象审核仍明确要求一个目标               |
| A08  | 批次、条件、参数宏、任务保留相同业务能力                        | 组合不是剥夺权限的理由，既有业务条件执行时复核               |
| A09  | 原子批次末尾检查自动完赛，无跨请求暂缓开关                      | 允许完整组合，避免新增长期比赛控制状态；完赛仍是终态         |
| A10  | 资源沿用科技0/1、光粒0/1、剩余广播0—2，但可反复补               | 加强管理而不新增弹药模型或改玩家发射流程                     |
| A11  | 主动光粒发放联动科技，已持有返回无变化                          | 一条管理指令即可完成，避免先升级再发弹的冗余                 |
| A12  | 自然技术爆炸沿原候选；指定奖励不受母星尚存/未升级限制           | 不将自然抽奖条件误用为裁判权力边界；仍须第一阶段正式存活     |
| A13  | 暂停仅保留在装备、资格恢复和复杂历史纠错等必要流程              | 发消息、奖励、随机淘汰、手动歌者不为此停全场                 |
| A14  | 主动恢复走现有待激活流程，保留现场佩戴和新码                    | 无须证明误判，也不直接给玩家写active逃过码核对               |
| A15  | 处罚可赦免、次数可重设，历史不删                                | 当前裁决与过去事实分开，原抽签不重新生成                     |
| A16  | 母星主动恢复限第一阶段原登记                                    | 避免改末日及后续玩家行动，恢复母星也不自动复活飞船           |
| A17  | 定时可调用强操作，任务确认即授权                                | 不要求裁判到点再点一次；未完成现场事实不能由时间代替         |
| A18  | 迟到run/skip/review可选，不一刀切五分钟丢弃                     | 默认消息run、强干预review；总裁判可明确授权强干预迟到run     |
| A19  | 事务通知允许赛后keep，正赛影响取消                              | 集合通知等不应因正常完赛消失，不借keep重开比赛               |
| A20  | 原时长与实际起始语义明确，静默可until-revoked                   | 不限30分钟，不用冻结时钟来替代长期禁攻                       |
| A21  | 输入256KiB、嵌套32层、单页1000条/1MiB为工程初值                 | 保留防资源耗尽边界，实施后依据测量调整，不称玩法规则         |
| A22  | 不固化50步、24小时、32标签等限制                                | 按实际执行预算判定；不能原子执行时明确提供逐步作业选择       |
| A23  | 参数范围按现有Schema，不另造一小时上限                          | 本轮不扩建参数体系，也不把未经核对的数字写成规则             |
| A24  | 允许选项任意顺序、本地带偏移时间、复合时长及多行                | 让解析器处理明确表示，不强迫裁判人工换算                     |
| A25  | 统计可选目标、字段、类别和窗口，三快捷项保留                    | 通过已有数据聚合增强，不做任意SQL或全历史快照引擎            |
| A26  | GUI、HTTP、宏、定时复用同一服务                                 | 管理服务可以局部扩展，不把新权限塞进玩家资格判断             |
| A27  | 自动/管理来源、原文日志、实际目标和结果均留档                   | 记录决定，不用日志要求反过来取消合法能力                     |
| A28  | 原始密钥、照片、GPS、独立部署恢复不进入控制台                   | 沿既有架构和权限划分，本轮不扩展基础设施工具                 |
