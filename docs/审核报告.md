## 发现

### F01 / P1：实际母星登记表单与后端Schema不兼容（复现）

网页apps/web/src/pages/player.tsx:292发送code与expected_version；apps/match-worker/src/services/player.ts:99只允许request_id、code，packages/contracts/src/backend.ts:27拒绝额外字段。按实际网页正文提交返回400 BAD_REQUEST，消息为请求包含不允许的字段。首个必要玩家流程即被阻断。

建议：统一实际表单、共享请求类型及服务端Schema，增加真实组件至HTTP/DO的登记验收。不能仅修正独立手写的后端请求测试。

### F02 / P1：正式名单之外的已审核母星仍参与广播匹配并获得反向情报（复现）

apps/match-worker/src/services/player.ts:482的广播匹配仅过滤code及verified，没有正式名单条件；snapshot.ts:197、454允许该候选账号读取自己的intel。正常接口先审核C04母星、正式名单仅选C01—C03，开赛后C01广播C04口令，C04仍能读取C01的真实母星口令。无须越权裁判身份。光粒匹配player.ts:518和歌者匹配scheduler/events.ts:170同样未限定正式母星范围，需要一起检查。

建议：冻结本场正式母星集合，所有广播、歌者、光粒、通知和情报授权沿用同一范围。

### F03 / P1：重生倒计时没有使用65分钟硬截止（复现数据，静态核对呈现）

player.ts:280、304设置被击毁时刻加respawnSeconds；snapshot.ts:127原样投影deadline；网页player.tsx:102、478直接展示；ui.tsx:312只做deadline减当前时刻。第60分钟死亡返回75分钟截止，网页显示15分钟，实际只有5分钟且服务器在65分钟淘汰。允许动作和服务器结算有硬截止，误导发生在展示层。

建议：投影并显示min(个人期限,65分钟)，测试默认及自定义重生参数的晚期死亡场景。

### F04 / P1：常规违规淘汰和跨阶段资格纠错缺少完整裁判入口（静态审查及命令复现）

judge.ts:21仅注册终局淘汰，终局之外没有一般裁判淘汰服务入口；commands.ts不识别/player eliminate。judge.ts:311将通用restore限制为第一阶段暂停、已淘汰且母星尚存，不能直接修复末日或终局人工误淘汰。attack_correction.ts是特定攻击撤销，不能替代人工淘汰纠错。账号停用也不会原子淘汰文明，不可用作替代。

依据：策划案§7.1、§12，技术方案§15.6、§20.6。建议补充受保护的赛事淘汰与恢复操作，统一更新码、航次、淘汰记录、观战、排名及通知。

### F05 / P1：失败到期事件阻断裁判自身的暂停与取消操作（故障注入复现）

engine.ts:561在进入任何普通裁判写服务之前调用settleDue；events.ts:48遇到失败会抛出。一个持续失败的到期song_visit使暂停预览、取消预览都返回503，无法到达相应管理服务。普通裁判快照读取同样先补结算。独立scheduler/health读接口可用，但不等于网页工作台和处置链可用。复现采用损坏事件负载模拟持续故障，不表示已在真实比赛自然遇到该故障。独立恢复密钥通道仍存在，但需要恢复材料和部署管理员。

建议：阻断玩家行动时仍保留权限受控、审计化的故障读取、暂停和处置通道。

### F06 / P1：固定间隔轮询在持续慢网下会丢弃全部已完成快照（受控前端函数复现）

state.tsx:175每次refresh增加sequence，只接受最新序号；state.tsx:426每2秒再次调用，缺少在途互斥。若每次响应均超过2秒，上一请求返回时已不再是最新，所有响应持续被丢弃，状态停留在旧快照。使用实际AppProvider代码与受控read完成顺序验证：有更新请求在途时完成3次读取，采纳0次，停止发新请求后最后一次才被采纳。此为函数级复现，不是手机弱网实测。

建议：单请求完成后再排下次刷新，或使用明确的在途合并策略；补充大于轮询间隔的延迟测试。

### F07 / P2：通知待办数量与优先级基于局部最新记录（复现）

judge_records.ts:20按最新位置逆序取100条，不先过滤未发送或按事件重要性排序；网页judge.tsx:193在这100条内计数。构造一条较早未发送击毁通知和100条较新的已发送通知，工作台显示待发送0条，数据库实际仍有1条。更早记录可以手动分页，不是数据被删除，但工作台待办统计不真实，也不符合失联/直接出局优先处理要求。

建议：服务端提供完整未发送计数和优先队列，历史发送记录另行分页。

### F08 / P2：高影响操作的预览大量使用占位文本（静态审查）

judge.ts:418—420默认返回before为当前已保存状态、after为前端传入change；仅参数、名单、暂停和终局核验有专门处理。资源修复、装备换码、攻击更正、账号操作等没有完整的实际前后值及连带影响清单。预览Token绑定、权限和版本校验存在，缺的是可供裁判作出知情确认的业务预览。

建议：各业务操作生成权威差异、受影响对象和连带动作，明确发码容量、观战变化及提前完赛影响。

### F09 / P2：指令历史和普通管理审计未保存足够的前后状态（静态审查）

commands.ts:83只读命令直接返回；副作用命令映射为judgeAction。judge.ts:896普通管理审计detail只有requestId，未记录原指令、参数、预览、完整前后状态。judge_records.ts:43直接把before投影为空字符串、gameMs设为0。schema.ts没有设计中的judge_command_log；部分攻击更正有独立前后快照，不能代表所有管理操作。通知状态judge.ts:568也覆盖operator，没有分别保留复制人/时间与发送人/时间。

建议：保存可检索的命令及业务审计记录，区分命令、预览、执行与失败，分开记录通知复制/发送履历。

### F10 / P2：事件管理部分操作只返回成功，未执行对应行为（复现与静态审查）

judge.ts:709仅实现cancel分支，retry无操作仍走通用成功响应。取消tech:0后执行retry返回200，事件仍cancelled。若已取消事件不允许重试，应明确拒绝而不是声称操作完成。/events list在commands.ts:73返回的是最近30条已发生event_log，不是计划队列；/events inspect、/event trigger也未实现。scheduled_events缺少attempt_count/last_error等逐事件诊断记录，仅有全局健康错误。

建议：明确区分安全重试、已结算幂等返回、取消后重开与新建事件，提供实际计划及失败详情。

### F11 / P2：基础目标选择器和历史查询能力缩水（部分命令复现）

commands.ts只支持若干命令中的@a或单个C编号；不支持@alive、@dead、@random[alive]或按状态过滤，网页judge.tsx:1052仍宣称这些目标可用。/history与/inspect走同一路径，返回当前文明快照及有限码航次，没有独立攻击、处罚、通知和纠错历史查询。原技术方案§15.6把更复杂的条件执行和宏列为扩展方向，不能仅因未实现宏就认定比赛核心失败；上述基础选择器、管理和诊断能力则有明确原文依据。

建议：以能力清单逐项验收，帮助与自动补全必须反映实际支持范围。
