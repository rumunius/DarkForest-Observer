# 《黑暗森林：观察者效应》技术方案

> 文档状态：工程实施依据｜Cloudflare Pages Functions + SQLite-backed Durable Objects  
> 技术目标：支撑120分钟三阶段生存淘汰赛与24人级别的实时目击判定  
> 权威数据：单场比赛SQLite-backed Durable Object；权威时钟：服务端双时基  
> 域名接入：阿里云权威DNS，通过自定义**子域名**接入Cloudflare Pages  
> 配套文件：黑暗森林_完整策划案.md

## 1. 技术目标与系统职责

系统采用Cloudflare Pages静态网页、Pages Functions同域HTTP接口、独立部署的SQLite-backed Durable Object Worker及其内置SQLite权威数据库，并通过阿里云DNS子域名提供访问。所有比赛状态写入同一场次对应的唯一Durable Object实例；服务端Alarms负责计划事件唤醒。QQ用于赛事通知与终局实时位置共享。业务模块包括七色手环目击码、350枚永久唯一发码簿、两侧颜色集合归一化、图形化攻击、失配判罚、母星登记、15分钟返航、三阶段时钟、广播、歌者、技术爆炸、光粒、终局排名、永久淘汰后的四维观测以及通用裁判指令控制台。

每名玩家的装备为同款同宽的七色手环各一条，出航时仅佩戴3—4条；仅允许`2+1 / 2+2 / 3+1`分组。**左右交换等价，同臂顺序无语义，编码仅由两臂颜色集合决定；重生以母星存亡和时限为准。** 本场已经发行的码无条件保留并永久不可复用，发码只校验本场唯一性。

### 1.2 系统与裁判职责

- **Cloudflare Pages：** 玩家/裁判网页，七色图形化目击输入、两臂佩戴示意、倒计时和终局地图。
- **Pages Functions：** 同域HTTPS API入口、请求大小与格式校验、会话Cookie及CSRF防护、将命令路由至当前比赛唯一Durable Object、按角色过滤响应与设置私有无缓存头；不直接持有可变比赛状态。
- **Durable Object Worker：** 通过`MATCH_DO`内部Binding暴露受控RPC，在一个场次对象中执行比赛事件屏障、码本、目击攻击、概率判罚、重生、广播、光粒、权限、阶段及裁判指令。
- **Durable Object SQLite：** 全部已发行码HMAC索引与密文、航次、攻击与抽签、母星六位口令、事件计划、战绩、人工淘汰记录、命令审计与QQ通知的唯一权威数据源。
- **Durable Object Alarms：** 依持久化计划安排下一次唤醒；自动结算到期事件，并处理异常重试与重新排程。
- **玩家：** 合规佩戴与摘下手环、本人现场观察及网页操作、母星登记和重生水印照片通过QQ发送。
- **裁判：** 手环颜色及同规格检查、母星与QQ照片审核、QQ通知、争议核验、比赛控制、终局QQ地图人工监看及淘汰，以及使用管理指令处置异常。
- **四维观察者：** 永久淘汰后步行返回中控室；通过只读赛事态势和现场讨论继续参与活动，遵守不向活人通风报信的君子协定。

**事务不变量：** 每次权威操作先处理T0/T1及到期事件；每场比赛仅一个确定性对象ID与SQLite状态源；同一目标现役码仅一笔攻击获胜；第二次失配只抽签一次；直接出局与母星状态、航次注销和淘汰记录原子提交；发码本场永久唯一；终局人工淘汰与开战指令原子结算；事件、通知及操作结果按稳定ID持久化且幂等。

## 2. 云端架构与基础设施

### 2.1 请求拓扑与权威边界

```text
中国大陆玩家 / 裁判手机 / 中控室浏览器
       │ HTTPS，仅访问 game.example.com
       ▼
阿里云权威DNS：game.example.com CNAME → <pages-project>.pages.dev
       │
       ▼
Cloudflare Pages：静态前端与 /api/* Pages Functions
       │ ① 同源Cookie、Origin/CSRF、请求大小与Schema
       │ ② 验证并选择当前match_id；生成可信入口UTC时间
       │ ③ MATCH_DO内部Durable Object Binding（RPC，无公网Worker URL）
       ▼
独立部署的 Worker：DarkForestMatch SQLite-backed Durable Object
       ├─ 唯一对象：MATCH_DO.getByName('match:' + match_id)
       ├─ 业务授权、单场规则结算与安全随机数
       ├─ SQLite：比赛状态、事件队列、身份会话、通知、审计
       ├─ transactionSync：同步读取、判定与多表原子更新
       └─ alarm()：唤醒、补结算、重排下一次Alarm

QQ比赛群/裁判私聊：人工发送公告、审核照片与终局实时位置共享
```

一场比赛只使用**一个确定性Durable Object对象ID**。生产、排练与本地场次使用不同的`match_id`、独立命名空间或清晰隔离的对象标识；任何玩家请求不得创建随机对象ID。所有权威写入只由场次对象内的业务方法执行，Pages Functions不执行独立写库、战绩修改或抽签。单场约24人共享一个强一致状态源，多个场次使用各自独立对象。

Durable Object通过Worker导出类，并由Pages内部绑定调用。该Worker不要求自定义域名、Route或可被玩家访问的`workers.dev`地址；生产部署配置`workers_dev:false`。客户端只调用Pages自定义域名下的同源`/api/*`。

### 2.2 阿里云DNS、Pages与HTTPS

1. 在Cloudflare创建Pages项目并部署静态文件与`functions/`接口目录。
2. 在Pages的`Custom domains`中添加**子域名**，例如`game.example.com`。
3. 阿里云继续担任权威DNS；新增`game`的CNAME记录，指向实际`<pages-project>.pages.dev`。
4. 确认Pages自定义域名验证与HTTPS证书就绪；不使用根域名作为本架构的Pages接入地址。
5. 现场核验校园Wi-Fi、中国移动、联通、电信以及QQ内置浏览器的页面、API与DO读写时延。

DNS只影响客户端到Pages入口的可达性；Pages至DO的调用使用Cloudflare内部Binding。生产页面全部必要的CSS、脚本、字体图标和终局地图自行托管，不依赖可能无法从中国大陆访问的外部CDN。

### 2.3 Durable Object部署与绑定

Worker的`wrangler.jsonc`示例：

```jsonc
{
  "name": "darkforest-core",
  "main": "src/index.ts",
  "compatibility_date": "2026-11-01",
  "workers_dev": false,
  "durable_objects": {
    "bindings": [{ "name": "MATCH_DO", "class_name": "DarkForestMatch" }]
  },
  "migrations": [
    { "tag": "v1", "new_sqlite_classes": ["DarkForestMatch"] }
  ]
}
```

Pages的`wrangler.jsonc`核心结构：

```jsonc
{
  "name": "darkforest-pages",
  "pages_build_output_dir": "./dist",
  "compatibility_date": "2026-11-01",
  "durable_objects": {
    "bindings": [
      {
        "name": "MATCH_DO",
        "class_name": "DarkForestMatch",
        "script_name": "darkforest-core"
      }
    ]
  }
}
```

Pages项目的Durable Object绑定也可通过控制台`Settings → Bindings → Durable Object`配置；绑定变更后重新部署Pages，确保生产与预览环境均指向预期的对象类。`new_sqlite_classes`负责创建SQLite存储后端；各业务表结构由场次对象的幂等schema初始化与版本化升级维护。

```ts
// Pages Functions，示意调用边界；鉴权与参数校验须由共用中间件完成。
const stub = context.env.MATCH_DO.getByName(`match:${validatedMatchId}`);
const result = await stub.dispatchAction({
  sessionToken: verifiedCookieToken,
  requestId: validatedRequestId,
  action: 'sighting',
  input: { arm_a, arm_b },
  edgeReceivedUtcMs: Date.now() // Pages受信入口时间；客户端不可覆盖
});
```

RPC仅传必要的结构化数据。对象内再次从会话表验证身份与权限；普通玩家不能选择任意`match_id`，登录时确定的场次与Cookie作用域需要一致。业务模块和导出的RPC方法均对外部HTTP不可直接调用。生产环境通过Secrets保存服务端HMAC、加密及会话相关密钥。

### 2.4 双时基与统一开赛

系统分别持久化**真实UTC时钟**和**有效比赛时钟**：

- T0 `code_release_at_utc_ms`：赛前发码权限的真实UTC生效点。到达后仅允许合格玩家领取首航`reserved`码，不进行正式攻防。
- T1 `started_at_utc_ms`：全员准备完成后总裁判锁定的未来UTC开赛点。全部`ready/reserved`航次在该点统一生效，比赛有效时钟从0:00开始。
- `game_ms`：比赛开始后`max(0, utc_now - T1 - total_paused_ms - current_pause_elapsed_ms)`，其中每段全场暂停区间在`clock_pauses`中保存。
- 个人错误攻击禁攻、四维观战180秒、管理员UTC临时效果：采用真实UTC，不随全场比赛暂停冻结。
- 15分钟重生期限、歌者、技术爆炸、65/90/98/120阶段节点：采用`game_ms`，暂停时冻结；98:00裁判核验暂停由终局截止事件自动开启。

`phase`保持实际赛程阶段（`forest/apocalypse/transfer/hunt`等），暂停状态由单独`is_paused`标志表示；`hunt_review_finalized_at_utc_ms`记录总裁判完成终局核验的真实UTC时刻，并与阶段、存活状态共同决定终局攻击门禁。98:00的`hunt_cutoff`事件自动创建`reason='hunt_review'`的暂停区间；总裁判通过`hunt-finalize`关闭该区间并结算资格淘汰。`clock_pauses`保存每段开始、结束、操作人、理由，将历史游戏有效时刻映射为相应UTC时刻。涉及系统延迟结算的记录同时保存`effective_game_ms`、`effective_utc_ms`与`committed_at_utc_ms`，不混用。

阶段节点（毫秒）为`0/3_900_000/5_400_000/5_880_000/7_200_000`。在节点整点先处理系统事件再处理玩家操作，故`65:00`重生、`90:00`攻击和`120:00`攻击均按边界规则判定。`98:00`进入终局资格截止状态并自动冻结有效比赛时钟；裁判完成淘汰名单核验后，`hunt-finalize`统一关闭核验暂停并恢复时钟；存活人数不超过1人时直接完赛。暂停指令只有在场次DO事务成功提交后生效，浏览器的断线、熄屏、计时器停止不会改变服务器时钟。

### 2.5 Alarms调度与入口补结算

每个场次对象维护一份SQLite `scheduled_events`计划表，按绝对UTC任务和有效比赛时间任务分类，所有未结算任务拥有稳定`event_id`。调度器从待处理记录计算**最近一个可执行UTC到期点**，使用`ctx.storage.setAlarm(nextDueUtcMs)`安排对象唤醒。一个DO同时只有一个Alarm，多个事件由一条持久化队列管理。新任务插入、任务取消、暂停、恢复、事件结算和管理员重新排程后都必须计算并维护下一次Alarm。

`alarm()`被触发时调用与玩家动作相同的`settleDueEvents`域结算器，按权威有效时刻及同刻优先级逐个原子提交；完成后安排最近的下一个Alarm。闹钟即使因平台调度稍晚执行，事件仍保留各自原始**生效比赛时刻**，并以真实提交UTC单独记账。每个重要玩家写请求和关键状态读取也触发到期补结算屏障，以覆盖闹钟延迟及恢复期间的积压。

暂停期间游戏有效时钟冻结：未到期的`game_ms`任务不产生未来UTC闹钟；恢复后根据暂停累计时长重算UTC唤醒点。绝对UTC的必要管理任务可继续安排。若已安排的Alarm在暂停后被唤醒，首先检查`is_paused`，不得提前执行游戏时钟事件。只有成功的调度和数据库确认才在健康面板记录正常；闹钟重新登记失败时产生可见告警，并在下一次对象RPC、Alarm重试或总裁判`rearm`指令中修复。

`alarm()`具备至少一次触发/失败自动重试特性，业务依靠状态条件、稳定事件ID及`UNIQUE`约束实现**效果恰好一次**；它不是硬实时计时器。裁判页面按需轮询仅用于刷新界面与通知列表，**赛事运行不以任何浏览器心跳为前提**。

### 2.6 现场责任边界

- **Pages与API：** 所有浏览器访问及认证请求使用同一个HTTPS子域名；不公开DO内部端点。
- **权威对象：** 维护业务状态、计划事件、玩家航次、永久码本、身份与权限、通知待办和审计。
- **Alarms：** 负责无人访问期间的主动服务端定时唤醒；实际执行时间受平台调度条件影响。
- **裁判：** 完成QQ公告和私聊、母星照片审核、终局QQ群地图人工判定、手动淘汰与开战、异常处理及安全巡查；核验暂停持续至总裁判提交资格裁决。
- **玩家：** 对自己的手环佩戴、返航照片和QQ流程负责，及时查看官网本人状态。

## 3. 身份、密钥与权限

### 3.1 玩家账号

赛前批量建立固定文明编号`C01`至`C24`，每人单独领取一次随机高熵登录口令。首次使用口令换取HTTP-only会话Cookie。会话设置`Secure`、`HttpOnly`、`SameSite=Lax`或更严格配置，所有写操作检查Origin与CSRF策略。

数据库只保存登录口令的安全摘要或HMAC；会话令牌亦存储摘要。管理员口令和玩家登录口令分离，裁判采用独立账号和最小权限。

### 3.2 不可修改昵称

昵称在首次注册确认或母星登记前设置。服务端执行：
- 格式、长度与唯一性检查；
- 统一Unicode正规化；
- 事务内锁定`nickname_locked_at`；
- 后续普通玩家接口无改名入口；
- 裁判更正需原因和审计日志。

所有公开和私密展示通过统一格式化函数生成：`C07·归零者`。数据库保存`civilization_id`和`nickname`两个独立字段；不可把昵称当作身份主键。

七色手环的两臂组合是现场目击码；它与文明编号、登录凭证分别属于独立字段和权限范围。

### 3.3 账号与权限角色

| 角色 | 权限 |
|---|---|
| 正常参赛玩家 | 仅本人当前可用动作、本人秘密母星/情报、公开宇宙信息 |
| 四维观察者 | 永久淘汰满180秒后，使用本人原账号读取全局赛事态势与已发生事件；所有赛事及裁判写接口均关闭 |
| 通讯/事件裁判 | 查看待发通知、复制文案、标记已发送、处理分配范围内异常 |
| 总裁判 | 开赛、全场暂停、恢复、阶段异常处理、纠错、淘汰复核、完整管理指令与导出结果 |

四维观战属于玩家账号在指定状态下获得的只读能力，`flights.status`仍为`eliminated`，不授予裁判角色或裁判会话。所有API按身份、当前状态、当前UTC时间和所请求的数据范围重新鉴权。

玩家行动API每次校验会话身份、比赛阶段、飞船状态、母星存亡、动作次数及其目标合法性。裁判写接口要求独立裁判会话和相应管理权限。

### 3.4 维度跃迁的授权条件

永久淘汰事务记录`eliminated_at_utc_ms`；观战解锁时刻由`eliminated_at_utc_ms + 180_000`确定。使用服务端真实UTC时间，比赛暂停时照常计时。玩家页面即时显示摘环、返回中控室提示及剩余秒数。

| 判定 | 玩家页面与接口权限 |
|---|---|
| `flights.status != eliminated` | 按正常赛事状态展示本人功能；没有四维观战入口 |
| `eliminated`且未满180秒 | 个人淘汰页面、返回中控室提示和观战倒计时；观战接口返回剩余等待时间 |
| `eliminated`且已满180秒 | 个人页面和只读「宇宙观测」接口；无玩家行动和裁判控制权限 |
| 裁判纠错使文明重新取得参赛资格 | 按纠错后的赛事状态即时核算权限，关闭四维观战入口 |

永久淘汰的来源包括失配直接出局、最后一命被击毁、重生超时、母星毁灭期间未出航、65分钟末日、98分钟裁判终局资格淘汰、终局离圈或共享中断的人工淘汰和正式退赛。恢复资格由裁判完成事务纠错，相关永久淘汰记录和观战授权随之修正。

## 4. 核心数据模型

### 4.1 核心标识与状态

| 名称 | 类型及核心不变量 |
|---|---|
| `match_id` | 单场持久化ID，唯一码范围按场隔离 |
| `player_id / nickname` | C01等文明编号与锁定昵称，不参与目击输入 |
| `homeworlds.code` | 六位十进制字符串`TEXT`，保留前导零 |
| `broadcasts.code / photon_shots.code` | 六位坐标字符串，与手环编码完全独立 |
| `COLOR_IDS` | `BK,WH,GY,YL,OR,SB,PU`，位0至6固定映射，不得更换顺序 |
| `arm_a / arm_b` | 网页提交颜色ID数组，仅表示任意两个手臂分组，无具体左右语义 |
| `canonical_key` | 一对不交叠7位集合掩码取数值较小者在前，以`min:max`拼接；不存储明文到普通日志 |
| `sighting_codes.code_mac` | `HMAC_SHA256(K_code, "bracelet|" + match_id + "|" + canonical_key)`；场内永久唯一 |
| `sighting_codes.code_ciphertext` | 加密存储规范码，用于本人待佩戴状态恢复与审计 |
| `sighting_codes.status` | `reserved/active/retired`；已发记录永不删除以确保不复用 |
| `flights.current_code_id` | 当前航次最多对应一枚尚未退役的码 |
| `flights.status` | `prelaunch/staged/outfitting/ready/active/returning/preparing/issued/eliminated` |
| `attack_controls.wrong_count` | 本场累计失配次数；退役旧码不计，重生和成功攻击不清零 |
| `attack_controls.locked_until_utc_ms` | 错误攻击后禁目击攻击的UTC截止时间，不提供免战 |
| `attacks.wrong_index / wrong_roll` | 本次失配序号；第二次失配记录服务器安全随机抽签数，仅裁判审计可见 |
| `attacks.direct_out` | 本次错误攻击是否导致直接出局，幂等保存 |
| `homeworlds.destroyed_at_game_ms` | NULL表示母星尚存；直接出局时若母星尚存则原子置毁灭 |
| `matches.phase` | `setup/armed/outfitting/start_countdown/forest/apocalypse/transfer/hunt/ended`；98:00进入`hunt`与核验暂停；终局目击需处于`hunt`、已完成核验且时钟运行 |
| `eliminations.eliminated_at_utc_ms` | 淘汰规则生效UTC；`committed_at_utc_ms`记录实际提交UTC；180秒观战以生效UTC为准 |
| `matches.ended_at_game_ms / finish_reason` | 实际完赛时刻及原因：120:00、只剩一名文明、全体淘汰 |
| `admin_effects` | 裁判命令产生的临时能力变化，按作用域与真实UTC期限生效 |
| `judge_command_log` | 管理指令的执行主体、来源、参数、预览、结果与审计信息 |
| `scheduled_events.kind` | `code_release/match_start/respawn_timeout/song_visit/tech_burst/apocalypse/transfer_start/hunt_cutoff/regulation_end` |

归一化码仅表示手环颜色分组；**不得**将本人文明编号、外貌、衣着、手环图案朝向或同臂先后顺序拼入码键。每场比赛使用一份全局唯一的发码簿。

### 4.2 数据表清单

| 表 | 职责 |
|---|---|
| `matches` | 首航T0/T1、阶段、有效比赛时钟与暂停 |
| `players` | 编号、昵称、光粒与广播额度 |
| `homeworlds` | 母星口令、版本、裁判审核与毁灭状态 |
| `flights` | 当前航次、码引用、准备、返航、出航和截止 |
| `sighting_codes` | 手环码HMAC与密文、本场发行、激活、退役及永久唯一索引 |
| `attack_controls` | 全部目击请求节奏、正式失配次数和禁攻截止 |
| `flight_history` | 航次、返航、佩戴就绪、发码及裁判纠错日志 |
| `attacks` | 每次目击结果、失配随机抽签与直接出局结果、幂等请求ID |
| `intel_grants` | 成功目击及广播获得的秘密母星情报 |
| `broadcasts / photon_shots` | 六位坐标广播与光粒事务 |
| `scheduled_events` | 歌者、技术爆炸、超时和阶段事件 |
| `event_log / eliminations` | 宇宙事件与永久淘汰游戏时间、真实UTC时间及审计记录 |
| `admin_effects` | 有期限的全局或定向临时能力控制 |
| `judge_command_log` | 裁判命令预览、执行、结果、用途与幂等记录 |
| `judge_hunt_actions` | 裁判终局开战和人工淘汰指令，保存裁判、文明、离圈或共享违规原因及操作时刻 |
| `notice_queue` | 裁判QQ待办、复制与发送状态 |
| `sessions / request_journal / audit_logs / rate_limits` | 登录、幂等响应、受限审计与非目击接口限速 |
| `clock_pauses / scheduler_health` | 全场暂停历史、预期Alarm、调度异常与恢复状态 |

数据模型通过`sighting_codes`的永久唯一索引管理码本，不需要额外的距离掩码表。正式赛事使用独立单场DO SQLite数据库，并在部署前校验所有发码约束。

### 4.3 SQLite-backed Durable Object主要数据库结构

以下SQL构成单场SQLite数据库的主要约束与业务表。每个Durable Object实例拥有独立SQLite空间；`sessions`、`request_journal`、`rate_limits`、`schema_meta`与部分审计辅助表也在**同一对象**持久化，由schema版本化初始化，不能把会话或战绩单独放到另一份非权威数据源。全部SQL使用绑定参数，不拼接客户端输入。下文示意SQL中的`:player_id`等具名占位符为描述用途；采用`ctx.storage.sql.exec()`实现时须转换为`?`占位符并按位置安全绑定实参。初始化执行后检查外键约束、唯一索引和关键字段是否按预期生效。

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE matches (
  id TEXT PRIMARY KEY,
  version TEXT NOT NULL DEFAULT 'official',
  phase TEXT NOT NULL DEFAULT 'setup',
  code_release_at_utc_ms INTEGER,  -- T0：开放首航发码
  code_release_settled_at_utc_ms INTEGER,
  started_at_utc_ms INTEGER,       -- T1：统一激活与正赛0:00
  start_settled_at_utc_ms INTEGER,
  armed_at_utc_ms INTEGER,
  start_countdown_armed_at_utc_ms INTEGER,
  is_paused INTEGER NOT NULL DEFAULT 0 CHECK(is_paused IN (0,1)),
  paused_at_utc_ms INTEGER,
  total_paused_ms INTEGER NOT NULL DEFAULT 0,
  hunt_review_finalized_at_utc_ms INTEGER,   -- 总裁判完成终局资格核验的真实UTC；NULL表示核验尚未完成
  scheduler_revision INTEGER NOT NULL DEFAULT 0,
  ended_at_utc_ms INTEGER,
  ended_at_game_ms INTEGER,             -- 完赛有效比赛时刻；常规完赛为7200000
  finish_reason TEXT CHECK(finish_reason IN ('regulation','last_survivor','all_eliminated')),
  created_at_utc_ms INTEGER NOT NULL
);

CREATE TABLE players (
  id TEXT PRIMARY KEY,
  match_id TEXT NOT NULL REFERENCES matches(id),
  nickname TEXT NOT NULL,
  nickname_locked INTEGER NOT NULL DEFAULT 0,
  entry_status TEXT NOT NULL DEFAULT 'registered'
    CHECK(entry_status IN ('registered','withdrawn')),
  tech_level INTEGER NOT NULL DEFAULT 0 CHECK(tech_level IN (0,1)),
  photon_remaining INTEGER NOT NULL DEFAULT 0 CHECK(photon_remaining IN (0,1)),
  broadcast_count INTEGER NOT NULL DEFAULT 0
    CHECK(broadcast_count BETWEEN 0 AND 2),
  created_at_utc_ms INTEGER NOT NULL,
  UNIQUE(match_id, nickname)
);
CREATE INDEX idx_players_match ON players(match_id);

CREATE TABLE homeworlds (
  player_id TEXT PRIMARY KEY REFERENCES players(id),
  match_id TEXT NOT NULL REFERENCES matches(id),
  code TEXT NOT NULL CHECK(length(code) = 6 AND code NOT GLOB '*[^0-9]*'),
  registration_status TEXT NOT NULL DEFAULT 'pending'
    CHECK(registration_status IN ('pending','verified','rejected')),
  submission_version INTEGER NOT NULL DEFAULT 1 CHECK(submission_version >= 1),
  submitted_at_utc_ms INTEGER NOT NULL,
  verified_submission_version INTEGER,
  verified_at_utc_ms INTEGER,
  verified_by TEXT,
  rejected_at_utc_ms INTEGER,
  rejection_reason TEXT,
  destroyed_at_game_ms INTEGER,
  destroyed_by_event_id TEXT
);
CREATE UNIQUE INDEX idx_verified_homeworld_code
  ON homeworlds(match_id, code)
  WHERE registration_status = 'verified';
CREATE INDEX idx_pending_homeworlds
  ON homeworlds(match_id, registration_status, submitted_at_utc_ms);

CREATE TABLE flights (
  player_id TEXT PRIMARY KEY REFERENCES players(id),
  match_id TEXT NOT NULL REFERENCES matches(id),
  status TEXT NOT NULL DEFAULT 'prelaunch'
    CHECK(status IN ('prelaunch','staged','outfitting','ready','active','returning','preparing','issued','eliminated')),
  voyage_no INTEGER NOT NULL DEFAULT 0,
  current_code_id TEXT REFERENCES sighting_codes(id),
  preflight_left_home_at_utc_ms INTEGER,
  preflight_staged_at_utc_ms INTEGER,  -- T0前尚未发行手环码
  preflight_ready_at_utc_ms INTEGER,   -- T0后手环佩戴完成
  respawn_deadline_game_ms INTEGER,
  destroyed_at_game_ms INTEGER,
  returned_photo_declared_at_game_ms INTEGER,
  left_home_declared_at_game_ms INTEGER,
  worn_confirmed_at_game_ms INTEGER,
  activated_at_game_ms INTEGER
);
CREATE INDEX idx_flight_code_id ON flights(match_id, current_code_id);

CREATE TABLE sighting_codes (
  id TEXT PRIMARY KEY,
  match_id TEXT NOT NULL REFERENCES matches(id),
  player_id TEXT NOT NULL REFERENCES players(id),
  voyage_no INTEGER NOT NULL,
  code_mac TEXT NOT NULL,
  code_ciphertext TEXT NOT NULL,
  status TEXT NOT NULL CHECK(status IN ('reserved','active','retired')),
  issued_at_utc_ms INTEGER NOT NULL,
  activated_at_game_ms INTEGER,
  retired_at_game_ms INTEGER,
  retired_at_utc_ms INTEGER,
  retired_reason TEXT,
  request_id TEXT NOT NULL,
  UNIQUE(match_id, code_mac),
  UNIQUE(match_id, player_id, request_id)
);
CREATE UNIQUE INDEX idx_one_unretired_code_per_player
  ON sighting_codes(match_id, player_id)
  WHERE status IN ('reserved','active');
CREATE INDEX idx_sighting_owner_voyage
  ON sighting_codes(match_id, player_id, voyage_no);


CREATE TABLE attack_controls (
  match_id TEXT NOT NULL REFERENCES matches(id),
  player_id TEXT NOT NULL REFERENCES players(id),
  wrong_count INTEGER NOT NULL DEFAULT 0,
  locked_until_utc_ms INTEGER NOT NULL DEFAULT 0,
  manual_lock INTEGER NOT NULL DEFAULT 0 CHECK(manual_lock IN (0,1)),  -- 仅裁判违规/技术锁定，非错码次数触发
  last_request_at_utc_ms INTEGER,
  total_attempts INTEGER NOT NULL DEFAULT 0,
  updated_at_utc_ms INTEGER,
  PRIMARY KEY(match_id, player_id)
);

CREATE TABLE flight_history (
  id TEXT PRIMARY KEY,
  match_id TEXT NOT NULL REFERENCES matches(id),
  player_id TEXT NOT NULL REFERENCES players(id),
  voyage_no INTEGER NOT NULL,
  event_type TEXT NOT NULL,
  at_game_ms INTEGER NOT NULL,
  actor TEXT NOT NULL,
  metadata_json TEXT NOT NULL DEFAULT '{}'
);
CREATE INDEX idx_flight_history_player ON flight_history(player_id, voyage_no);

CREATE TABLE attacks (
  id TEXT PRIMARY KEY,
  match_id TEXT NOT NULL REFERENCES matches(id),
  attacker_player_id TEXT NOT NULL REFERENCES players(id),
  target_player_id TEXT REFERENCES players(id),
  code_id TEXT REFERENCES sighting_codes(id),
  attempted_code_mac TEXT,
  request_id TEXT NOT NULL,
  edge_received_at_utc_ms INTEGER NOT NULL,
  committed_at_utc_ms INTEGER,
  request_digest TEXT NOT NULL,
  at_game_ms INTEGER NOT NULL,
  at_utc_ms INTEGER NOT NULL,
  successful INTEGER NOT NULL DEFAULT 0 CHECK(successful IN (0,1)),
  valid INTEGER NOT NULL DEFAULT 1 CHECK(valid IN (0,1)),
  counted_wrong INTEGER NOT NULL DEFAULT 0 CHECK(counted_wrong IN (0,1)),
  wrong_index INTEGER,
  wrong_roll INTEGER CHECK(wrong_roll BETWEEN 0 AND 99),
  direct_out INTEGER NOT NULL DEFAULT 0 CHECK(direct_out IN (0,1)),
  result_kind TEXT NOT NULL,
  UNIQUE(match_id, attacker_player_id, request_id)
);
CREATE INDEX idx_attacks_distinct_kills
  ON attacks(match_id, attacker_player_id, successful, valid, target_player_id);
CREATE INDEX idx_attacks_target_time ON attacks(match_id, target_player_id, at_game_ms);
CREATE INDEX idx_attacks_player_utc ON attacks(match_id, attacker_player_id, at_utc_ms);

CREATE TABLE broadcasts (
  id TEXT PRIMARY KEY,
  match_id TEXT NOT NULL REFERENCES matches(id),
  sender_player_id TEXT NOT NULL REFERENCES players(id),
  code TEXT NOT NULL CHECK(length(code) = 6 AND code NOT GLOB '*[^0-9]*'),
  request_id TEXT NOT NULL,
  broadcast_at_game_ms INTEGER NOT NULL,
  singer_due_game_ms INTEGER,
  singer_status TEXT NOT NULL DEFAULT 'unscheduled',
  singer_settled_at_game_ms INTEGER,
  UNIQUE(match_id, code),
  UNIQUE(match_id, sender_player_id, request_id)
);
CREATE INDEX idx_broadcasts_sender ON broadcasts(match_id, sender_player_id);

CREATE TABLE photon_shots (
  id TEXT PRIMARY KEY,
  match_id TEXT NOT NULL REFERENCES matches(id),
  shooter_player_id TEXT NOT NULL REFERENCES players(id),
  code TEXT NOT NULL CHECK(length(code) = 6 AND code NOT GLOB '*[^0-9]*'),
  request_id TEXT NOT NULL,
  fired_at_game_ms INTEGER NOT NULL,
  result_kind TEXT NOT NULL DEFAULT 'pending',
  victim_player_id TEXT,
  UNIQUE(match_id, shooter_player_id),
  UNIQUE(match_id, shooter_player_id, request_id)
);

CREATE TABLE scheduled_events (
  id TEXT PRIMARY KEY,
  match_id TEXT NOT NULL REFERENCES matches(id),
  kind TEXT NOT NULL,
  source_event_id TEXT,
  clock_kind TEXT NOT NULL DEFAULT 'game' CHECK(clock_kind IN ('game','utc')),
  due_game_ms INTEGER,
  due_utc_ms INTEGER,
  priority INTEGER NOT NULL DEFAULT 50,
  payload_json TEXT NOT NULL DEFAULT '{}',
  status TEXT NOT NULL DEFAULT 'pending' CHECK(status IN ('pending','settled','cancelled')),
  attempt_count INTEGER NOT NULL DEFAULT 0,
  last_error TEXT,
  effective_at_utc_ms INTEGER,
  settled_at_utc_ms INTEGER,
  CHECK((clock_kind='game' AND due_game_ms IS NOT NULL) OR (clock_kind='utc' AND due_utc_ms IS NOT NULL)),
  UNIQUE(match_id, kind, source_event_id)
);
CREATE INDEX idx_due_game_events
  ON scheduled_events(match_id, status, clock_kind, due_game_ms, priority, id);
CREATE INDEX idx_due_utc_events
  ON scheduled_events(match_id, status, clock_kind, due_utc_ms, priority, id);

CREATE TABLE intel_grants (
  id TEXT PRIMARY KEY,
  match_id TEXT NOT NULL REFERENCES matches(id),
  recipient_player_id TEXT NOT NULL REFERENCES players(id),
  home_owner_player_id TEXT NOT NULL REFERENCES players(id),
  code TEXT NOT NULL,
  source_event_id TEXT NOT NULL,
  granted_at_game_ms INTEGER NOT NULL,
  UNIQUE(match_id, recipient_player_id, home_owner_player_id, source_event_id)
);

CREATE TABLE eliminations (
  player_id TEXT PRIMARY KEY REFERENCES players(id),
  match_id TEXT NOT NULL REFERENCES matches(id),

  eliminated_at_utc_ms INTEGER NOT NULL,
  committed_at_utc_ms INTEGER NOT NULL,
  ordering_seq INTEGER NOT NULL,
  simultaneous_group_id TEXT,
  reason TEXT NOT NULL,
  source_event_id TEXT

  ON eliminations(match_id, eliminated_at_game_ms DESC, ordering_seq DESC);

  ON eliminations(match_id, eliminated_at_utc_ms);

  match_id TEXT NOT NULL REFERENCES matches(id),
  opened_at_utc_ms INTEGER NOT NULL,
  closed_at_utc_ms INTEGER,
  opened_by TEXT NOT NULL,
  closed_by TEXT,
  reason TEXT NOT NULL,

CREATE TABLE judge_hunt_actions (
  id TEXT PRIMARY KEY,
  match_id TEXT NOT NULL REFERENCES matches(id),
```

### 4.4 权威状态、索引和操作不变量

1. **单场唯一权威源：** `getByName('match:' + match_id)`确定唯一对象；一场比赛的一切可变状态只写入该对象SQLite。
2. **350码精确枚举：** 稳定颜色ID为`BK,WH,GY,YL,OR,SB,PU`；仅允许`2+1/2+2/3+1`、两臂交换等价和同臂无序。离线断言350种。
3. **永久唯一发行：** `UNIQUE(match_id,code_mac)`涵盖`reserved/active/retired`全部历史码；`idx_one_unretired_code_per_player`限制单人未退役码数量。
4. **单航次一次击毁：** 目标`active`和现役码条件更新只允许唯一获胜者；额外业务写入均在同一`transactionSync`提交。
5. **单次失配一次判罚：** 命中、自码、格式/资格拒绝、重试与经审计的真实竞速例外不增加`wrong_count`；正式失配在同一事务确定次数、抽签与处罚。
6. **错误出局与淘汰：** 本人母星、当前码、航次、`eliminations`与通知事务化；已永久淘汰不重复生效。
7. **事件顺序：** 对`scheduled_events`按有效时刻、同刻优先级、稳定事件ID逐项结算；单一事件状态只可从`pending`进入`settled/cancelled`一次。
8. **定时唤醒：** SQLite计划是权威；Alarm是执行机制；入口补结算、独立唤醒及调度健康恢复共同保证不因客户端休眠而遗漏业务事件。
9. **终局人工执裁：** 98:00自动冻结有效时钟并关闭目击；裁判通过QQ地图决定截止资格名单，`hunt-finalize`单事务淘汰名单、结束核验暂停并决定开战或完赛。开战后离圈或共享中断由裁判逐人处理。
10. **业务与认证：** `sessions`、`request_journal`、`audit_logs`、`notice_queue`均在相同DO存储；同一请求ID加请求摘要保证可验证的重放结果。
11. **事务与异步：** 业务事务中的读、条件分支与多表更新须完全同步；随机数使用同步安全随机源，HMAC/AES需要的异步计算在事务外完成且最终以事务内重新核验为准；`transactionSync`回调内不得`await`。
12. **权限隔离：** 普通用户可读取本人的目击结算与处罚，其他文明的码归属、完整目标坐标及未来随机计划依角色权限开放；四维观察者180秒后读取已发生的赛事态势；裁判写入经过角色鉴权和审计。

## 5. 七色手环码与攻击控制

### 5.1 七色字典、合法分组与容量

颜色ID及位顺序**一旦赛事初始化便不可修改**：

```ts
export const COLORS = [
  { id: 'BK', name: '黑色' },
  { id: 'WH', name: '白色' },
  { id: 'GY', name: '灰色' },
  { id: 'YL', name: '黄色' },
  { id: 'OR', name: '桔色' },
  { id: 'SB', name: '天蓝色' },
  { id: 'PU', name: '紫色' },
] as const;
```

`arm_a`及`arm_b`是任意两侧手臂的颜色ID集合，不携带生理左手/右手语义、同臂先后顺序、内外面朝向或任何外貌字段。每枚码中每种颜色至多出现一次。允许的两侧数量无序组合只有`2+1`、`2+2`与`3+1`。

```text
2+1：C(7,3)×3 = 105
2+2：C(7,4)×3 = 105
3+1：C(7,4)×4 = 140
合计：350枚（严格有限）
```

玩家每人携带七色各一条，出航时佩戴3或4条，其余收入口袋。24人首航后剩326枚发行容量；异常作废或领码后未激活也占用历史码本。**重生不设累计次数上限，全场采用统一码本，不复用本场历史码。**

### 5.2 规范化编码（同臂无序、双臂交换等价）

用7位整数掩码表示各侧颜色集合。掩码位`i`严格对应`COLORS[i]`，如`BK`是位0、`WH`位1。数值较小的掩码写在前，生成`"smaller:larger"`格式的内部规范键；这只是服务器内部表示，不是玩家必须记忆或填写的文字码。

```ts
const COLOR_IDS = ['BK','WH','GY','YL','OR','SB','PU'] as const;
const bitIndex = new Map(COLOR_IDS.map((id, i) => [id, i]));
function countBits(n: number): number {
  let bits = 0;
  while (n) { n &= n - 1; bits++; }
  return bits;
}
function armMask(ids: readonly string[]): number {
  if (!Array.isArray(ids)) throw new Error('invalid arm');
  let mask = 0;
  for (const id of ids) {
    const i = bitIndex.get(id as typeof COLOR_IDS[number]);
    if (i === undefined) throw new Error('unknown color');
    const bit = 1 << i;
    if (mask & bit) throw new Error('duplicate color');
    mask |= bit;
  }
  return mask;
}
export function normalizeSighting(armA: string[], armB: string[]): string {
  const a = armMask(armA), b = armMask(armB);
  if (a === 0 || b === 0 || (a & b) !== 0) throw new Error('invalid sets');
  const pair = [countBits(a), countBits(b)].sort((x, y) => x - y);
  const shape = pair.join('+');
  if (!['1+2', '2+2', '1+3'].includes(shape)) throw new Error('invalid shape');
  return `${Math.min(a,b)}:${Math.max(a,b)}`;
}
export function enumerateAllCodes(): string[] {
  const out = new Set<string>();
  for (let a = 1; a < 128; a++) for (let b = a + 1; b < 128; b++) {
    if (a & b) continue;
    const pair = [countBits(a), countBits(b)].sort((x,y) => x-y).join('+');
    if (['1+2','2+2','1+3'].includes(pair)) out.add(`${a}:${b}`);
  }
  if (out.size !== 350) throw new Error(`codebook size ${out.size}`);
  return [...out].sort();
}
```

两臂交换、相同臂内数组顺序交换，规范结果必须不变；非法形状、重复颜色、非字典颜色或空臂要直接拒绝，**不能**将非法状态当作有效失配并触发直接出局。客户端和服务端共用相同稳定规则；服务器是最终权威。

### 5.3 密钥索引、随机发行与容量不足

本场每次发行只从`enumerateAllCodes()`生成的350枚规范键中选择**尚未出现于本场发码簿**的一个。用服务端安全随机数进行候选顺序洗牌，并在事务中插入：

```text
code_mac = HMAC_SHA256(K_code, "bracelet|" + match_id + "|" + canonical_key)
code_ciphertext = AES-GCM(K_enc, canonical_key, nonce, AAD=match_id+issue_id)
```

`UNIQUE(match_id, code_mac)`覆盖所有发行记录，状态为`retired`的旧码也不得再次选择。发码校验仅以350种合法配置、规范化HMAC索引和本场永久唯一性为准。

发行事务必须核验本人处于正确航次准备阶段、尚无非退役当前码、母星及截止时刻合法；在同一事务中插入`sighting_codes`并绑定`flights.current_code_id`，最终向本人返回解密后的**两侧颜色数组**。重试同一`request_id`返回原先同一结果，不再占用第二枚码。

为了避免随机拒绝采样在码空间即将耗尽时无谓失败，可以取当前尚未使用的完整规范键列表、使用`crypto.getRandomValues`作无偏洗牌并按先后顺序尝试插入。并发唯一冲突后重新读取未用列表；当全部350个码确实已发放，返回专用内部`CODEBOOK_EXHAUSTED`，写入严重告警并阻止该次发码，**不能**秘密复用旧码、另设编号时代或暗中降低某人的重生资格。需要由总裁判统一暂停并公开处置；这是有限容量的硬限制，不是个人重生预算。

后台私有统计：`issued_count = COUNT(sighting_codes WHERE match_id=...)`；`available_count=350-issued_count`，计入所有`reserved/active/retired`发行记录。显示20、10、0的预警阈值，仅面向裁判，不能在普通玩家网页泄漏精确发码簿。

### 5.4 首航、现役、退役与手环实物状态

| 状态 | 手环实物 | 服务端意义 |
|---|---|---|
| `staged` / 首航T0前 | 手中七色材料包，尚无本场佩戴码 | 不能攻防 |
| `reserved` / 首航准备 | 按T0官网图示佩戴3或4条，其余放入口袋 | 码已永久占用，T1前不能攻防 |
| `active` | 双臂正确展示本航次的3或4条比赛手环 | 当前可被目击攻击；若未禁攻也可主动目击 |
| `retired` / 被击毁 | 在安全位置摘下所有比赛手环 | 旧码永久失效，可正常返航（仅母星尚存且正常被击毁时） |
| `reserved` / 重生准备 | 返航及离巢时无佩戴，领码后在安全位置按新图示佩戴 | 尚未出航，不可攻防 |
| `retired` / 直接出局、退赛、异常作废、赛事结束 | 摘下全部手环 | 不得再受理该码，永久保留历史 |

首航：`staged → outfitting → ready → active`；重生：`returning → preparing → issued → active`。T0首航发码只是`reserved`，T1才原子全部激活。重生`launch`提交成功才恢复攻防，完整的手环佩戴须先在安全位置完成。

### 5.5 目击结果分类与失配口径

攻击接口接收`{request_id,arm_a,arm_b}`，将两臂颜色集合归一化后计算`code_mac`，在本场永久发码簿内判定：

| 后台结果 | 判定 | 攻击效果 | 失配计数 |
|---|---|---|---|
| `hit` | 匹配另一名合法`active`玩家的当前码，事务胜出 | 击毁目标、授予母星情报 | +0 |
| `self_code` | 属于攻击者本场任一航次的码 | 无效 | +0 |
| `lost_race` | 请求受理期间同一现役目标先被其他攻击击毁，有可信并发记录 | 无效 | +0 |
| `retired_code` | 匹配本场他人已退役或已注销的历史码 | 无效目击 | +0 |
| `reserved_code` | 匹配另一名玩家尚未激活的已发行码 | 进入失配判罚 | +1 |
| `unknown_code` | 合法350码之一，本场尚未发行 | 进入失配判罚 | +1 |
| `bad_format` | 颜色、分组或其他格式非法 | 拒绝受理 | +0 |
| `duplicate/throttled/ineligible` | 幂等重试、节流、阶段或状态不允许 | 拒绝受理 | +0 |

失配计数整场累计，跨航次保留。已经退役的本场旧码始终不计失配，包括目标被击毁后较晚提交的旧码。未命中统一展示「本次目击未产生击毁」，附本人累计失配次数、实际禁攻期限与淘汰状态；后台保留结算分类。

### 5.6 第1、2、3次错误攻击与禁攻

服务器在一次`transactionSync`中完成`wrong_count`累加、处罚、攻击记录与幂等结果。仅在**第二次失配**使用服务器安全随机数抽取`wrong_roll`（0—99等概率）：

| `wrong_index` | `wrong_roll`条件 | 结果 |
|---:|---|---|
| 1 | 无须抽签 | 保持正常出航，禁目击攻击300秒（5分钟） |
| 2 | 0—49 | 直接永久淘汰 |
| 2 | 50—99 | 保持正常出航，禁目击攻击900秒（15分钟） |
| 3 | 无须抽签 | 直接永久淘汰 |

第二次失配使用`crypto.getRandomValues`及无偏映射生成0—99整数。第一、三次失配的`wrong_roll=NULL`。同一`request_id`重试返回原有结算，第二次失配的抽签结果持久保存。

「直接出局」使攻击者本人永久淘汰；若母星尚存，同事务将母星判毁灭。当前码退役，写入`eliminations(reason='wrong_attack_direct_out')`、私人通知和审计。此次淘汰不增加其他文明的目击战绩，玩家也不具备15分钟重生资格。

禁攻时`attack_controls.locked_until_utc_ms=now_utc_ms+300000/900000`，按真实UTC运行。全场暂停期间禁攻时间继续经过，`wrong_count`保留。禁攻玩家仍为`active`，可以被目击；其他合法广播、光粒和外交继续开放。合法重生后仍在禁攻截止时间内的玩家继续禁攻。

请求节流与本人现场目击要求适用于全部有效攻击；服务端按发码簿判定命中、退役旧码及正式失配。

### 5.7 通用限速与故障安全

每账号受理目击请求至少间隔4秒、滚动60秒最多10次、单场超过120次需总裁判复核。通用节流先于规范码查询；网络重试使用稳定`request_id`。不同请求反复提交同一个未发行码或他人待激活码，每次正式受理均累计失配；提交本场已退役旧码则不累计。

普通玩家的未命中提示统一使用「本次目击未产生击毁」，并展示本人当前失配次数与适用的禁攻剩余时间；裁判受限审计查看后台分类、`wrong_index`、第二次抽签结果及结算UTC时间。数据库异常时必须回滚攻击及处罚，不允许命中成立却未完成目标退役，也不允许抽签完成却没记录错误次数。

## 6. 统一规则结算入口

### 6.1 每个业务RPC的统一处理顺序

```text
Pages Functions：同域HTTP → Cookie/Origin/CSRF/格式检查
  → 从服务端会话绑定的场次取得match_id，生成edge_received_at_utc_ms
  → MATCH_DO.getByName('match:' + match_id).dispatchAction(...)
  → DO内从sessions验证身份、角色与请求ID
  → 计算当前权威UTC及有效比赛时刻，检查已有request_journal
  → 在同一个场次对象中结算已到期的T0/T1及所有游戏事件（含重生超时）
  → 读取最新阶段、本人状态、限制与资源
  → 同步transactionSync：检查资格 → 业务读写 → 事件、审计、通知及幂等结果
  → 提交完成后维护下一次Alarm；异常则上报调度健康
  → 返回本人允许查看的结果、服务器时间与allowed_actions
```

Pages负责公共HTTP安全防护，DO负责**最终角色与赛事授权**。不得仅依据前端隐藏按钮、Pages传入的`player_id`或客户端倒计时授予比赛资格。跨对象状态写入被禁止；所有关键规则判断都在同一实例的同步SQLite事务中完成。

### 6.2 赛程阶段与权限屏障

| 阶段 | 权威生效条件 | 允许动作 |
|---|---|---|
| `setup` | 名单登记与母星审核 | 母星、昵称、离巢准备 |
| `armed` | T0已锁定但未到 | 只读倒计时 |
| `outfitting` | T0已到且T1未锁定 | 本人领取首航码、佩戴并确认就绪 |
| `start_countdown` | T1已锁定但未到 | 只读开赛倒计时 |
| `forest` | 有效时间`[0,3_900_000)` | 目击、重生、广播、光粒及宇宙行为 |
| `apocalypse` | `[3_900_000,5_400_000)` | 目击、外交；全体母星已毁 |
| `transfer` | `[5_400_000,5_880_000)` | 裁判在QQ监看共享地图、玩家步行入圈；拒绝目击 |
| `hunt` | `[5_880_000,7_200_000)` | 裁判手动淘汰不合格者并确认开战；开战后合格存活者目击、持续QQ共享 |
| `ended` | `>=7_200_000` | 只读战报与复盘 |

`is_paused=1`时拒绝一切会改变正式战局的普通玩家操作，允许总裁判恢复、必要管理与观察者UTC解锁；有效时间停止，个人禁攻UTC时钟和180秒观战时钟继续流逝。`hunt`阶段在核验暂停期间或`hunt_review_finalized_at_utc_ms`尚未写入时持续拒绝目击攻击；结算为`ended`后统一拒绝玩家行动。任何阶段在尚未持久化事件结算的情况下，都按当前权威时间进行逻辑门禁，不能凭阶段字段未更新许可已过期行动。

### 6.3 T0与T1原子屏障

T0权限依预定UTC开放，本人申请时可在同一场次对象完成`armed→outfitting`结算；DO Alarms同时主动安排T0到期唤醒。每人首航码仅在本人合法领取时发行，未发码者不会因为T0触发而占用编码。

T1在所有正式参赛者`ready/reserved`后由总裁判锁定未来UTC。T1到期，系统在一个`transactionSync`中核验名单数、逐人将`ready→active`、对应手环码`reserved→active`、标记赛事进入`forest`，写统一开赛事件及待发QQ公告，全部激活使用同一有效比赛时刻0:00。异常必须整笔回滚，不得只激活部分玩家。

### 6.4 同步SQLite事务模板

```ts
// Durable Object类的方法内部。以下展示原子更新与校验形式。
function settleTargetHit(sql, storage, { targetId, codeId, nextStatus, gameMs }) {
  return storage.transactionSync(() => {
    const hit = sql.exec(
      `UPDATE flights
       SET status = ?, current_code_id = NULL, destroyed_at_game_ms = ?
       WHERE player_id = ? AND status = 'active' AND current_code_id = ?
       RETURNING player_id`,
      nextStatus, gameMs, targetId, codeId
    ).toArray();
    if (hit.length !== 1) throw new Error('TARGET_NOT_ACTIVE');

    const retired = sql.exec(
      `UPDATE sighting_codes SET status = 'retired', retired_at_game_ms = ?
       WHERE id = ? AND status = 'active' RETURNING id`, gameMs, codeId
    ).toArray();
    if (retired.length !== 1) throw new Error('CODE_RETIRE_CONFLICT');
    // 同步写入攻击、情报、重生或淘汰、通知、审计及幂等结果。
    // 任一步throw则本次事务全部回滚。
    return { targetId, status: nextStatus };
  });
}
```

示例中省略的完整攻击资格、重生期限、母星判断与通知写入必须按§7和§8实现，不能仅执行示例两条SQL即宣布成功。`transactionSync`回调必须是同步函数，不得执行`await`、外部网络请求或异步`crypto.subtle`运算。HMAC与AES-GCM可在事务前安全准备候选值，事务内部再依据最新SQLite状态验证资格、唯一性及条件写入；判罚抽签使用事务内同步`crypto.getRandomValues`。

`UPDATE...RETURNING`修改0行是业务条件失败，应抛错并回滚本次相关写入，或者在同一事务内按规则明确返回无效结果。**0行不等于SQL异常**。提交成功后才返回效果并安排Alarm，回包超时则依持久化`request_journal`恢复确定的结果。

### 6.5 事件到期的先后顺序

首先按`effective_game_ms`升序处理已到期游戏事件。相同有效游戏时刻的优先级为：

1. T1统一开赛及65/90/98/120分钟阶段边界；
2. 15分钟重生期限到期；
3. 歌者到访与技术爆炸，按固定事件ID进一步排序；
4. 玩家在该有效时刻提出的合法行动（由DO权威受理时刻及必要时的可信Pages入口时间界定）。

T0按真实UTC独立结算。事件可能在墙上时钟稍晚提交，但其规则生效时刻、同时淘汰组与排名始终由原计划决定。若系统存在积压，先对所有更早事件进行补结算，再受理当前玩家动作。绝对UTC临时效果由条件判定自然到期；如需发送到期通知，则使用`clock_kind='utc'`的计划事件。

### 6.6 对象休眠、Alarm重试与故障隔离

Durable Object对象实例可以被平台回收并重新实例化，持久SQLite和已登记Alarm不以对象内存中的计数器或JavaScript计时器为权威。构造时仅执行幂等建表和schema版本检查，不直接以首次构造时间初始化赛程时钟。

一次Alarm可能因至少一次触发语义被重复调用，或因系统维护而延迟。事件处理采用`pending→settled`的条件更新和业务唯一键；通知队列用`dedup_key`，资源扣减和同一事件效果同事务完成。若某个事件持续失败，记录异常并让平台重试，同时阻断后续可能破坏公平性的玩家写操作，等待受控恢复，不得悄悄跳过失败事件。

### 6.7 幂等请求与竞速证据

所有有副作用的接口必须携带`request_id`。`request_journal`保存`actor_id + request_id + action_kind + request_digest + result_json`，重复同ID且相同摘要直接重放同一结果；同ID不同请求内容返回`409 REQUEST_ID_CONFLICT`，不得二次抽签或发码。

Pages在进入应用时生成可信`edge_received_at_utc_ms`，DO另记`committed_at_utc_ms`。同一目标在请求受理期间被另一名玩家先击毁时，符合§7.2的竞速证据则记录`lost_race`。其他已经退役的历史码记录为`retired_code`；两类结果均不累计失配。

## 7. 目击攻击与去重战绩

### 7.1 目击攻击接口

`POST /api/action/sighting`

```json
{
  "request_id": "8fd1d70b-9e86-4a9f-92d2-b18c5d827401",
  "arm_a": ["BK", "OR"],
  "arm_b": ["WH"]
}
```

`arm_a`、`arm_b`表示两臂无序颜色集合，没有固定左右含义。交换两个数组时，服务器归一化得到相同规范码。攻击Schema只包含`request_id`及这两个颜色数组，任何额外字段均被拒绝。

服务端处理顺序：

1. 校验会话、Origin/CSRF、请求ID，记录服务器接收UTC时刻。
2. 结算T0/T1和全部应先发生的重生、歌者和阶段事件；处于T1前、比赛暂停、转场或结束则拒绝。
3. 校验本人`flights.status='active'`；在`hunt`阶段还需确认总裁判已开放终局攻击；查询同`request_id`历史结果并幂等返回。
4. 执行账号通用请求节流、错误攻击禁攻、裁判临时效果等门禁；被任何禁攻效果拒绝的请求均不得触发失配抽签。
5. 验证`arm_a`、`arm_b`为合法七色码，调用§5.2规范化并计算HMAC，在同场码簿查找。
6. 如果属于本人任何航次码，按`self_code`无效处理。若恰为另一名合法现役飞船当前码，则进入目标条件更新并争夺唯一成功权。
7. 命中成功则一次性退役目标码、更新目标返航/淘汰状态、写攻击战绩、向攻击者授予母星情报并向目标发送失联QQ待办。
8. 若并发请求争夺同一目标，仅第一笔成功；后续请求依据可信受理时间记录为`lost_race`或`retired_code`，均不计失配。
9. 对本场已退役旧码或本人码返回无效目击；对尚未发行码或他人待激活码按§5.5—5.6累计失配，第一次禁攻5分钟，第二次50%永久淘汰或50%禁攻15分钟，第三次永久淘汰。

命中和失配必须互斥；同一个提交不可能既击毁别人又直接出局，也不能因为原子写入失败而同时被记录为两种结果。

### 7.2 唯一击毁、目标退役与真实并发竞速

场次DO内的权威事务以**现役码仍对应另一名`active`目标**作为命中前提。条件更新`flights.current_code_id=:matched_code_id AND flights.status='active'`必须影响恰好一行；在同一同步事务内：退役目标当前码、生成目标返航或永久淘汰状态、在第一阶段计算固定的重生截止、写入攻击和目标母星情报、添加通知队列及`request_journal`结果。任何一步不满足预计行数均回滚，再依据当前权威状态重新分类或返回可重试的系统冲突。

归一化后合法但没有命中其他有效现役码的请求分为`self_code`、`lost_race`、`retired_code`、`reserved_code`、`unknown_code`。前三项不累计失配；后两项触发累计失配及5/15分钟UTC禁攻或直接出局。格式、阶段、会话、冷却和频率拒绝均不累计失配。

**真实竞速的判定证据：**

- 该码属于某个已经激活的目标航次，且目标码`retired_reason='hit'`，存在确实胜出的`hit`攻击事件与该码对应。
- 本次请求的可信`edge_received_at_utc_ms`由Pages Functions在通过HTTP入口时生成并传入DO，不能来自客户端；其时间**不早于该航次激活UTC**且**不晚于胜出攻击提交的退役UTC**。
- 该请求入口时间距离胜出攻击的码退役UTC不超过`500ms`，并满足当时玩家身份、阶段、冷却及通用频率门禁；该窗口是服务器内部竞速识别上限，不对玩家开放查询。
- 胜出事务和竞速请求均在同场单一DO对象审计中留存可信UTC、码ID、胜出事件ID；不能仅靠用户自述或客户端时间认定。

符合全部条件返回`lost_race`。超过竞速窗口或在退役后到达的本场旧码返回`retired_code`，均不累计失配；他人待激活码归入`reserved_code`，累计失配。裁判可依据入站时间与退役日志复核并发结果，验收使用跨设备并发和边界±500ms测试。

**唯一胜者：** 同一`code_id`只允许一次成功`hit`，重试同一`request_id`重放原结果；其他合法旧码提交不得误伤新的航次。本场码本永久唯一，目标重新出航只领取未曾出现的合法新配置。

### 7.3 去重目击战绩

本人成功目击击毁的**不同文明数**来自合法已结算`attacks`记录：

```sql
SELECT COUNT(DISTINCT target_player_id) AS unique_sight_kills
FROM attacks
WHERE match_id = :match_id
  AND attacker_player_id = :me
  AND successful = 1
  AND valid = 1;
```

同一攻击者对同一文明无论成功击毁多少航次，最多累计1次；首次成功击毁另一文明才增加一次。六位坐标广播、歌者、光粒、重生超时与阶段末日不构成目击战绩。经裁判核查撤销违规攻击后，将相应`attacks.valid=0`并重新汇总。

比赛中本人网页可以实时看到本人的`unique_sight_kills`；其他文明的击毁数与全场排行只有正式比赛结束后才公开。

### 7.4 幂等、审计与裁判纠错

`attacks`和`request_journal`通过场次/玩家/请求ID约束幂等；请求正文的规范摘要被固定，同一ID同一正文返回原结果，同一ID不同正文返回`409 REQUEST_ID_CONFLICT`。绝不重新抽取直接出局概率、发放第二枚手环码、重新扣广播或生成第二份事件。

攻击日志在受限SQLite中保存规范码HMAC、分类、可信Pages入口UTC、DO提交UTC、`wrong_index`、随机判罚值、是否直接出局及相关竞速证据；普通响应不展示历史码的发行或退役信息。裁判仅凭充分证据可恢复错误判罚，并同步检查码本、航次状态、观战权限、已泄露情报和排名；纠错发生在DO原子事务内且留下前后快照及原因。已经注销的编码仍永久不能复用。

QQ通知发送时间不改变权威生效时刻和重生截止。玩家合法攻击生效后，目标网页下一次读取状态即可看到被击毁，裁判仍需优先发送QQ私聊提醒。

## 8. 首航统一激活、重生时限与消息复制

### 8.1 母星提交、QQ核对与裁判审核

官网提供`POST /api/action/homeworld-submit`：玩家提交六位口令与幂等请求ID，服务器在`setup`阶段保存该文明的一条待审核记录，首次`submission_version=1`，后来提交递增版本，并生成玩家可复制的登记QQ消息。保存待审核记录不需要裁判二次键入六位数字。

```json
{
  "request_id": "homeworld-submit-001",
  "code": "001234"
}
```

玩家QQ私聊消息包含`C07·归零者`、六位坐标、**提交版本号**和24小时有效期说明，并附带母星现场时间水印照片。裁判在后台以玩家ID和最新版提交记录核对消息、照片、合法步行区域与母星实际地点后，调用`POST /api/judge/homeworld/:id/verify`：

```json
{
  "request_id": "homeworld-verify-001",
  "expected_version": 2,
  "expected_code": "001234",
  "decision": "verify"
}
```

服务端在条件写入中要求`registration_status='pending'`、`submission_version=:expected_version`、`code=:expected_code`且尚未锁定开赛。`verified_submission_version`固定批准的版本，`verified_by`和审核时刻写入审计。`idx_verified_homeworld_code`拒绝同一六位口令第二次通过，即使两个裁判同时点击也只有一个审核成功。被驳回的玩家收到原因并重新提交；后续QQ消息按新版本核对。

示例审核SQL：

```sql
UPDATE homeworlds
SET registration_status = 'verified',
    verified_submission_version = :expected_version,
    verified_by = :judge_id,
    verified_at_utc_ms = :now_utc_ms
WHERE player_id = :player_id
  AND match_id = :match_id
  AND registration_status = 'pending'
  AND submission_version = :expected_version
  AND code = :expected_code
  AND EXISTS (
    SELECT 1 FROM matches
    WHERE id = :match_id AND phase = 'setup'
  )
RETURNING player_id, code, submission_version;
```

前端在提交后显示「待审核」和当前口令版本；点击复制只使用**已保存的版本**生成模板。玩家重新提交会使之前QQ消息版本过期，裁判只能审核匹配的最新版。首航准备的数据库门禁只承认`verified`母星。

### 8.2 赛前首航准备与装备

```text
setup / prelaunch
  → 玩家官网提交母星口令、裁判对照QQ水印照片审核verified
  → 玩家离母星≥50米，确认七种颜色各一条的普通魔术贴手环齐备
  → POST /api/action/preflight-stage，进入staged（尚未获得任何手环码）
  → 裁判确认全部正式参赛者staged，锁定未来T0
  → T0后本人官网领取一个全场未使用的两臂颜色配置，码reserved
  → 玩家在安全位置戴好3—4条，未用手环放口袋，点击「穿戴就绪」
  → flights.status=ready，当前码仍reserved，暂不允许攻防
  → 全部ready后锁定未来T1，全体等待统一倒计时
  → T1到达，将全部ready/reserved原子变为active
  → 比赛时钟正式开始，T1之后现场重新目击才合法
```

`POST /api/action/preflight-stage`仍只在`setup`开放；要求母星`verified`、离巢50米、本人声明七色材料齐全、官网登录状态有效。此时`current_code_id=NULL`。

`POST /api/action/preflight-issue-code`仅在`outfitting`且T0之后可用。只给本人展示当前待佩戴的两侧颜色集合，不允许读取其他人当前码。重复请求返回同一已发行码；不会额外消耗容量。

`POST /api/action/preflight-ready`要求本人`outfitting`且码`reserved`，声明已在安全位置按图示佩戴3—4条手环、其余收起。T1到达前该码只是准备码，不可受攻击也不可主动攻击。T1前观察到他人的配置不得用于正式攻击。

### 8.3 名册锁定、T0发码与T1激活

`POST /api/judge/arm-code-release`在`setup`阶段检查全部正式参赛者均为`staged`、已离巢50米、已审核母星，再设置未来T0（例如服务器当前时间后60秒）并将`matches.phase='armed'`。T0的时间戳存储于`code_release_at_utc_ms`，裁判QQ群公示发码倒计时；名单在此时锁定，不接受新增正式参赛者。

```sql
UPDATE matches
SET phase = 'armed',
    code_release_at_utc_ms = :t0_utc_ms,
    armed_at_utc_ms = :now_utc_ms
WHERE id = :match_id
  AND phase = 'setup'
  AND (SELECT COUNT(*) FROM players
       WHERE match_id=:match_id AND entry_status='registered') >= 2
  AND NOT EXISTS (
    SELECT 1 FROM players p
    LEFT JOIN flights f ON f.player_id=p.id
    LEFT JOIN homeworlds h ON h.player_id=p.id
    WHERE p.match_id=:match_id AND p.entry_status='registered'
      AND (f.player_id IS NULL OR f.status<>'staged'
        OR f.preflight_left_home_at_utc_ms IS NULL
        OR f.current_code_id IS NOT NULL
        OR h.player_id IS NULL OR h.registration_status<>'verified')
  )
RETURNING code_release_at_utc_ms;
```

T0到达后，`settleCodeRelease`利用`code_release_at_utc_ms`条件地将`armed → outfitting`，写入`code_release_settled_at_utc_ms`，允许本人调用领取接口。发码簿的`UNIQUE(match_id,code_mac)`在每次领取事务中保证本场永久唯一；码配置仅凭规范化值进行唯一性校验，多位玩家同时领取也不会重复分配码。比赛有效时钟此时尚未启动。

`POST /api/judge/arm-start`仅在`outfitting`阶段允许调用，总裁判核对所有正式参赛者都已`ready`且有对应`reserved`码后，保存未来T1（建议当前时间后30秒），`matches.phase='start_countdown'`。该事务的就绪门禁在数据库内执行：

```sql
UPDATE matches
SET phase='start_countdown',
    started_at_utc_ms=:t1_utc_ms,
    start_countdown_armed_at_utc_ms=:now_utc_ms
WHERE id=:match_id AND phase='outfitting'
  AND NOT EXISTS (
    SELECT 1 FROM players p
    LEFT JOIN flights f ON f.player_id=p.id
    LEFT JOIN sighting_codes c ON c.id=f.current_code_id
    WHERE p.match_id=:match_id AND p.entry_status='registered'
      AND (f.player_id IS NULL OR f.status<>'ready'
        OR f.preflight_ready_at_utc_ms IS NULL
        OR c.id IS NULL OR c.status<>'reserved'
        OR c.player_id<>p.id OR c.match_id<>:match_id)
  )
RETURNING started_at_utc_ms;
```

T1到来时，`settleMatchStart()`按预定时刻在同一SQLite同步事务中：

1. 条件把`matches.phase='start_countdown' → 'forest'`，设置`start_settled_at_utc_ms`。
2. 将正式参赛者`flights.status='ready' → 'active'`，`activated_at_game_ms=0`。
3. 将各自`sighting_codes.status='reserved' → 'active'`，`activated_at_game_ms=0`，保持所有历史已发行码记录。
4. 写入统一开赛记录和裁判QQ通知待办，核对激活的飞船数与正式名单人数一致。

全部首航码在T1对应的比赛0:00同时生效。玩家是否保持网页前台、浏览器是否关闭，都不改变从T1起的出航资格。T0至T1期间提交的任何目击或宇宙行动按阶段拒绝，不累积`wrong_count`，也不消耗广播/光粒次数。

无法完成穿戴的玩家由总裁判在T1锁定前进行审核，必要时从正式名单中退出并将其已发行的`reserved`码退役；T1倒计时在其余正式参赛者全部`ready`之后才能锁定。任何错误重试不得绕过名册门禁。

### 8.4 重生的单一15分钟期限与手环换码

第一阶段只有被其他玩家**有效目击击毁**且母星仍存活的飞船才能进入普通重生流程；错误攻击触发直接出局者不允许进入该流程。规则不设置个人累计重生次数或额外冷却。

```text
death_game_ms = 被有效目击击毁的服务器游戏时刻
respawn_deadline_game_ms = death_game_ms + 900000
实际最迟重新出航 = min(respawn_deadline_game_ms, 3900000)（要求严格早于截止）
```

被击毁的当前码同事务`active→retired`，飞船`active→returning`并清除当前码引用；玩家在安全位置摘下所有比赛手环，不能再被目击攻击。

```text
active / 双臂佩戴现役手环
  └─ 正常目击击毁：当前码退役；全部摘环 → returning
       └─ 步行返航、母星水印照片发QQ → preparing
            └─ 继续不佩戴手环，离巢≥50米 → 发行全新的两臂配置、issued
                 └─ 安全位置佩戴3—4条、未用环放口袋、点击「完成出航」 → active
```

| 接口 | 操作和状态 |
|---|---|
| `GET /api/player/templates/respawn` | 取当前重生QQ私聊模板，玩家发送并附水印照片 |
| `POST /api/action/return-confirm` | 已返航、拍照并向QQ裁判发送后确认，`returning→preparing` |
| `POST /api/action/issue-code` | 已声明离母星≥50米且仍有时间，发行本场未用的新配置，`preparing→issued` |
| `POST /api/action/launch` | 本人确认双臂按新图示正确佩戴，`issued→active`且码`reserved→active` |
| `GET /api/player/self` | 本人当前重生截止与待佩戴配置（仅准备状态），禁攻未结束时额外显示UTC倒计时 |

所有动作须发生在同一次截止时间之前；如果中途母星被歌者/光粒毁灭或者65:00到达时仍未出航，则永久淘汰，待激活码退役并永久占用码本。已经成功重生的玩家不再受到之前的返航超时事件影响。错误攻击造成的禁攻跨合法重生持续，不改变返航期限或步骤。

### 8.5 消息复制、通知与手环设备异常

母星登记和重生页保留「复制QQ消息」按钮，浏览器优先使用`navigator.clipboard.writeText()`，失败则显示可手动选择的文本；复制不等于QQ已经发送。裁判端独立记录`copied`与`sent`状态。

手环损坏可经裁判用**同色同规格**备用环替换，且保持当前码不变。手环误戴、遗失或现役配置不可辨认时，玩家应停止主动行动并联系裁判；确需注销旧码重发，应先由总裁判统一暂停，事务化退役旧码、选择本场未用的合法两臂配置，完成佩戴确认后再激活并恢复比赛。换码仍然算发码历史消耗，绝不复用旧码或扩展码本。

## 9. 官网广播、歌者、光粒与技术爆炸

### 9.1 六位坐标输入规则

官网正式广播和光粒发射统一使用单个输入字段：

```json
{ "code": "000000" }
```

服务端验证格式：

```ts
const isCoordinateCode = (value: unknown): value is string =>
  typeof value === "string" && /^[0-9]{6}$/.test(value);
```

输入值按`TEXT`原样保存：`"000000"`、`"001234"`、`"739216"`均合法。服务器**不要求输入文明编号、不请求高德地理编码API、不校验口令在高德是否可导航**。

母星登记采用单独的裁判审核流程，只有`homeworlds.registration_status='verified'`的六位口令作为正式母星参与命中。官网行动只在成功消耗资源后，按六位字符串与已核验母星进行匹配。玩家、QQ群公开公告都不会在广播瞬间得到坐标真实性判断。

### 9.2 官网正式广播

`POST /api/action/broadcast`

```json
{
  "request_id": "f1eb089b-3b72-459a-9b6b-7e9ee20067d7",
  "code": "001234"
}
```

**身份资格：** `forest`阶段、发报飞船`active`、未永久淘汰、`players.broadcast_count < 2`。发报文明的母星可以已毁灭。

**坐标资格：** 正好六位数字、本场`broadcasts`中不存在相同六位字符串。目标是否在高德有效、是否真的有文明、母星是否已经毁灭，均不属于受理条件。

成功广播在一个SQLite同步事务内执行：

1. 根据发报者状态与剩余额度，条件插入新的`broadcasts`记录。
2. 将发报者`broadcast_count`增加1。
3. 为该坐标预先生成首次歌者清理计划（§9.4）；若第一阶段内没有抽到清理，则记录无计划到访。
4. 新增公开`event_log`：发报文明编号及昵称、广播口令、发生时刻。
5. 若六位口令匹配**任何已核验母星**，向实际母星拥有者写入`intel_grants`：发报源母星口令及其存亡状态；生成仅该文明可见的私聊待办。
6. 生成裁判QQ群正式广播公告任务，内容仅包含广播者及六位坐标。

**广播结果API：** 只向发报者返回`accepted=true`、本次公开广播事件ID、剩余次数；不返回`matched_homeworld`、命中文明、母星状态、秘密歌者计划。即便实际匹配了空坐标，也与真实母星使用相同成功文案。

**失败情形：** 输入格式不符、该六位口令已有官网广播记录、发报者次数用尽、飞船不具资格等返回相应错误。这些错误由本人资格或公开广播记录可确定，不暴露任何母星真实归属。失败请求不扣广播次数。

广播者可广播自己的母星口令，此时他自己收到反向情报，歌者也可按计划摧毁该母星。广播任何六位口令都占用发报者两次总额度中的一次。

### 9.3 广播原子事务与防双重扣除

`broadcasts.UNIQUE(match_id,code)`保证同一六位坐标每场只能正式广播一次；发报者`broadcast_count`最大为2。广播RPC先完成到期事件屏障，在DO的`transactionSync`中：

1. 核验本人`active`、`forest`阶段、已用次数小于2且该坐标从未正式广播；
2. 以唯一事件ID插入`broadcasts`，若唯一冲突则本次广播无效且不扣额度；
3. 确认插入恰好成功后加一次`broadcast_count`，并生成独立歌者计划或记录第一阶段内无可用检定窗口；
4. 按已审核母星口令精确匹配反向情报，写本人及目标的授权通知、公开公告与`request_journal`；
5. 任一必要步骤失败整笔回滚，不得出现已扣额度却没有广播事件的状态。

`request_id`重放同一结果，不扣第二次额度。广播是否对应真实母星和秘密歌者到访时刻只保留在授权数据中，发报者即时返回`accepted=true`、事件ID和剩余额度。

### 9.4 歌者首次清理时刻的生成

每条已受理正式广播坐标拥有一份独立的歌者首次清理计划。以广播受理时的**有效游戏时刻`broadcastAtGameMs`**为起点，每满60秒才进行一次5%独立检定；每次未抽中则继续下一完整60秒。若某次抽中，唯一清理事件计划在本次60秒窗口的**结束时刻**执行。广播后不足60秒的尾段没有检定，不存在本次广播后立刻到访的情况。

```ts
const FOREST_END_MS = 65 * 60_000;
const MINUTE_MS = 60_000;
function uniformInt(maxExclusive: number): number {
  const range = 2 ** 32;
  const limit = range - (range % maxExclusive);
  const sample = new Uint32Array(1);
  do { crypto.getRandomValues(sample); } while (sample[0] >= limit);
  return sample[0] % maxExclusive;
}
function firstSongDue(broadcastAtGameMs: number): number | null {
  for (let window = 1; broadcastAtGameMs + window * MINUTE_MS < FOREST_END_MS; window++) {
    if (uniformInt(100) < 5) {
      return broadcastAtGameMs + window * MINUTE_MS;
    }
  }
  return null;
}
```

计划时间严格早于65:00。若所有完整窗口均未抽中，就没有该坐标的歌者清理事件，并将广播歌者状态记为`not_selected`。每条坐标最多抽出一次首次到访；多个坐标相互独立，不因真实/空坐标数量改变各自概率。10个完整窗口内至少一次清理概率`1−0.95^10≈40.13%`，20个为`64.15%`，30个为`78.54%`。

广播当下的抽签结果和未来到访时间保留在DO受限SQLite，只有已发生的事件可进入普通公开API及四维观测历史。全场最多24×2=48条广播，因而至多48条歌者首次到访计划事件。

### 9.5 歌者到期结算

到达`song_visit.due_game_ms`时，结算器以该事件存储的六位字符串查询：

```sql
UPDATE homeworlds
SET destroyed_at_game_ms = :due_game_ms,
    destroyed_by_event_id = :song_event_id
WHERE match_id = :match_id
  AND code = :broadcast_code
  AND registration_status = 'verified'
  AND destroyed_at_game_ms IS NULL
RETURNING player_id, code;
```

若更新了一行：登记母星被歌者摧毁，调用统一的飞船末日状态处理与永久淘汰逻辑。生成QQ群公告（清理坐标、被毁文明编号+昵称）和母星毁灭私聊。

若更新了0行：完成一次**未摧毁现存母星的清理**。原因可能为空口令、高德无效口令、已毁母星口令，公开文案统一为“清理完成，未摧毁任何现存母星”。

`scheduled_events`状态仅由`pending`变为`settled`一次；`broadcasts.singer_status`同步标记；`event_log`记录实际清理时刻、内部匹配结果与公开可见结果。

事件若因后台暂时离线而迟到，使用原`due_game_ms`处理所有更早事件，确保与后续光粒或玩家动作的先后关系。事务并发校验保证同一母星只被一个清理事件首次摧毁。

### 9.6 秘密技术爆炸

总裁判锁定T1时，系统读取正式参赛名册中的文明数量 `N`，计算第一阶段技术爆炸总次数：

`M = min(max(1, round(N/3)), floor((N-1)/2))`

该公式会让技术爆炸次数随参赛规模增加而增加，同时始终控制在开赛文明总数的一半以下。典型取值为：5人局2次、12人局4次、24人局8次、36人局12次。

锁定T1的事务为第一阶段第8—55分钟随机排定 `M` 个秘密技术爆炸时刻，并让事件自然分散；常规规模下可优先保持相邻事件间隔约4分钟，人数较多时允许适度缩短。事件到期时，从母星**仍存且尚未升级**的文明中均匀抽取中奖者，允许该文明飞船正在返航。若事件到期时没有符合条件的文明，则该事件写入日志后直接结算完成，不补抽新对象。

成功升级后：
- 设置`tech_level=1`、`photon_remaining=1`。
- 写入仅裁判和本人有权查看的秘密事件。
- 生成该玩家的技术爆炸QQ私聊待办。
- 高级文明身份不在QQ群或公开API披露。

升级者须使飞船处于`active`才能使用光粒。母星后来毁灭不清空已获得的舰载光粒；第一阶段结束（65:00）后未使用的光粒统一失效。每个文明最多通过技术爆炸升级一次，已经升级者不再参加后续技术爆炸抽取。

### 9.7 光粒发射

`POST /api/action/photon`

```json
{
  "request_id": "85af7a74-6592-4a07-835a-af7cd3469b5b",
  "code": "000000"
}
```

服务端资格：`forest`阶段、发射者飞船`active`、未永久淘汰、`tech_level=1`、`photon_remaining=1`、六位数字格式正确。**发射者母星存亡不影响舰载光粒资格。**

发射成功时在同一SQLite同步事务内：
1. 插入光粒发射事件，写入秘密发射者、六位口令与有效时间。
2. 将发射者`photon_remaining`从1减少到0。
3. 按`homeworlds.code`精确匹配仍存活且已核验的登记母星，并尝试条件摧毁。
4. 命中真实尚存母星时，按§9.8处理其飞船状态并生成公开命中公告及目标私聊。
5. 无尚存母星匹配时，记录清理结果`empty`，生成“未摧毁现存母星”的QQ群公告。
6. `event_log`保存内部结果，公开事件隐藏发射者身份。

**光粒成功发射即消耗一枚**。无论口令能否在高德解析、是否有文明、母星是否早已毁灭，都属于已发射事件。发射前不提供任何真实性鉴定；发射后公众通过QQ群看到此次清理结果。

发射接口对本人立即返回“光粒已发射”、事件ID、剩余库存0。真实命中信息作为**行动完成后的公开事件**展示，发射者身份不进入公开公告。

### 9.8 统一母星毁灭结算

`destroyHomeworld(playerId, sourceKind, eventId, gameMs)`是统一的逻辑域操作，物理实现由SQLite同步事务SQL组合完成：

1. 仅对`destroyed_at_game_ms IS NULL`的目标母星条件写入毁灭时间与来源事件ID。
2. 根据目标飞船此刻状态处理：`active`保留最后一命；`prelaunch/returning/preparing/issued`立即永久淘汰。
3. 已永久淘汰文明的状态和排名不再次变化。
4. 保留目标飞船持有的剩余正式广播额度及已获得光粒，直到其权限随阶段结束或永久淘汰而失效。
5. 为实际毁灭写入公开事件，目标玩家生成QQ母星毁灭私聊待办；若同时永久淘汰，提示永久淘汰结果。
6. 歌者和光粒只争夺**尚存母星的首次毁灭权**，后到事件记录为“未摧毁现存母星”。

**事务写入必须只依据成功条件更新的结果生成命中事件**，不能依据先前查询结果假设母星仍存。空坐标结果在对应行动的事务中确定，通知补齐器根据持久化结算记录形成最终文案。

### 9.9 QQ公开事件与反向暴露

官网广播公布：发报者文明编号+昵称、六位坐标。广播成功时查出该六位口令在`homeworlds`是否登记过；若登记过，向其实际拥有者的`intel_grants`添加广播源母星口令及状态，并生成该拥有者的QQ私聊任务。**该匹配结果不作为广播API对发报者的返回字段，也不进入公开广播公告。**

歌者与光粒实际摧毁母星时，群公告展示被毁文明编号、昵称及坐标；没有摧毁尚存母星时，只展示坐标及“未摧毁任何现存母星”。光粒发射者字段只允许本人和授权裁判读取。

### 9.10 歌者、技术爆炸和阶段事件调度

第一阶段歌者、按参赛人数计算的`M`次技术爆炸、15分钟重生截止、65/90/98/120分钟阶段节点统一持久化至DO SQLite的`scheduled_events`。标准24人局`M=8`，事件在8—55分钟随机分布；相邻技术爆炸优先合理错开，允许同游戏时刻存在不同类别事件。

每当广播产生歌者事件、光粒摧毁母星、重生建立或完成、裁判暂停/恢复及计划任务增删时，场次DO根据待办任务重新安排最近一次Alarm。Alarm触发与玩家写请求共享§6和§16的同一个事件结算器，避免不同入口采用不同判定规则。事件QQ公告由事务写入`notice_queue`，裁判后台上线后按队列发送。未来事件计划不发送给普通玩家。

## 10. 第65分钟：宇宙末日

`scheduled_events.kind='apocalypse'`，`due_game_ms=3_900_000`。处理该事件时，先结算所有更早到期的歌者与技术爆炸事件。

同一SQLite同步事务完成：
1. 将所有当时仍存活的`homeworlds`标记为在65:00毁灭，来源`universe_end`。
2. 所有`flights.status='active'`的飞船保持出航状态，生命状态成为最后一命。正式参赛者的首航在0:00已由统一开赛事件激活。
3. 所有`prelaunch/ready/returning/preparing/issued`飞船永久淘汰；正常开赛后不会遗留`prelaunch/ready`首航飞船。
4. 本次批量淘汰者共用`simultaneous_group_id='apocalypse:<match_id>'`，淘汰时刻均为`3_900_000`。
5. 第一阶段广播、光粒、重生及技术爆炸的行动权限随阶段关闭；既有库存保留为战报历史，不具后续攻击效力。
6. 赛事阶段进入`apocalypse`，生成一次QQ群全域末日公告，为被直接淘汰者生成QQ私聊待办。

本次全域毁灭公告只公布宇宙末日结果，不公开仍未正式暴露的母星口令。

`apocalypse`处理必须幂等，连续触发或重复请求不得重复写入毁灭与淘汰记录。阶段结算与群公告使用同一源事件去重键。

## 11. 第90、98、120分钟：终局时序

### 11.1 第90分钟：暂停目击与开启位置共享

`scheduled_events.kind='transfer_start'`，`due_game_ms=5_400_000`。

服务器切换为`transfer`，隐藏玩家目击入口并拒绝攻击接口，生成QQ群阶段公告：

```text
【最后的狩猎】
第90分钟开始转场，目击攻击暂停。
请立即加入比赛QQ群的实时位置共享，并步行进入公布的终局圈。
第98分钟为位置共享和入圈截止时刻，裁判将人工核查并淘汰违规文明。
终局资格确认后，由总裁判宣布恢复攻击。
```

裁判在比赛QQ群发起共享实时位置，监看地图并核对幸存者的群名片与当前位置。网站向玩家展示静态终局地图、比赛时间和群共享操作说明。

### 11.2 裁判对终局位置的现场判定

实时位置仅在QQ群共享会话中由裁判查看。裁判从90:00持续监看共享地图，结合实际步行边界、临场巡查和合理定位误差判断玩家的入圈与共享情况。比赛98:00为资格判定截止时刻。

裁判管理页面展示仍存活文明名单，并允许裁判依据QQ地图**人工选择**待淘汰文明及原因。裁判可用的截止原因是`no_share_at_cutoff`（未按时加入共享）或`outside_at_cutoff`（截止时仍在圈外）。这些是裁判提交的赛事裁决字段；服务器接收文明编号和原因文字，不接收经纬度、QQ位置图像、位置轨迹或共享状态快照。

### 11.3 第98分钟：人工核验与资格结算

`scheduled_events.kind='hunt_cutoff'`，`due_game_ms=5_880_000`。到期事务将阶段切换为`hunt`、关闭目击门禁，写入`is_paused=1`与`clock_pauses(reason='hunt_review',opened_by='system')`，并保持`hunt_review_finalized_at_utc_ms=NULL`。暂停起点取有效比赛时钟98:00所映射的UTC，`game_ms`冻结在`5_880_000`。即使Alarm稍晚唤醒，也按原事件时刻建立核验暂停，随后事件结算停在98:00，等待总裁判完成资格审核。

总裁判根据QQ群共享地图与现场裁判核实截止资格，在管理页面执行`POST /api/judge/hunt-finalize`，携带人工确定的违规文明名单及原因。该受保护指令在**一笔同步事务**中：

1. 检查当前处于`hunt`阶段、`is_paused=1`且唯一开放中的暂停区间为`hunt_review`，并检查提交目标的存活资格。
2. 对名单中的文明执行永久淘汰、退役当前码，写入`eliminations`、`judge_hunt_actions`、赛事审计和私人通知；同批淘汰以`5_880_000`为生效游戏时刻、以该时刻映射的UTC为生效UTC，共用`simultaneous_group_id='hunt_cutoff:<match_id>'`。
3. 将`hunt_review_finalized_at_utc_ms`写为本次指令提交的真实UTC时刻，记录`finalize_hunt_review`人工裁决；同时关闭`hunt_review`暂停区间、更新`total_paused_ms`并解除`is_paused`。
4. 统计仍有参赛资格的文明。若数量至少为2，开放其余合格飞船的目击门禁、生成终局开战公告，并从有效时钟98:00起运行22分钟狩猎；若数量为1或0，依§11.6立即结算完赛。
5. 持久化同一`request_id`的结果。重复提交返回原响应，第二份核验名单由总裁判通过审计化纠错处理。

裁判提交示例：

```json
{
  "request_id": "hunt-finalize-001",
  "eliminations": [
    { "player_id": "C07", "reason": "no_share_at_cutoff" },
    { "player_id": "C12", "reason": "outside_at_cutoff" }
  ]
}
```

该指令可以携带空淘汰名单。裁判负责现场资格判断，服务器执行人工名单对应的游戏状态事务。核验暂停期间全场有效比赛时钟停在98:00；`hunt-finalize`完成后，终局时钟才继续推进至120:00。通用`/api/judge/resume`对`hunt_review`返回受控拒绝，核验暂停由`hunt-finalize`统一结束。

### 11.4 最后狩猎期间的持续执裁

开战后，裁判持续监看QQ群共享地图及现场情况。玩家离开终局圈、停止实时位置共享、使用虚拟定位或由他人代持手机，由裁判作出裁决，并通过`POST /api/judge/hunt-eliminate`手动永久淘汰。对应原因采用`left_zone`、`sharing_stopped`或`location_violation`，淘汰生效时刻取该指令实际服务器提交时刻。

终局持续执裁的提交示例：

```json
{
  "request_id": "hunt-eliminate-004",
  "player_id": "C18",
  "reason": "left_zone"
}
```

每次人工淘汰只保存文明编号、裁判、枚举原因、操作时间和关联赛事事件。QQ共享地图由QQ群承载，已淘汰玩家停止共享并返回中控室。

### 11.5 第120分钟：常规完赛

`scheduled_events.kind='regulation_end'`，`due_game_ms=7_200_000`。结算器调用统一完赛事务：
1. 关闭所有正赛行动，将`matches.phase`标记为`ended`，记录`ended_at_game_ms=7_200_000`、`ended_at_utc_ms`和`finish_reason='regulation'`。
2. 固定结束时仍存活的文明名单，按有效目击击毁过的不同文明数降序排名，同数并列。
3. 已淘汰文明排在幸存者之后，依淘汰生效时刻和并列淘汰事件组计算名次。
4. 取消尚待执行的正赛计划事件，生成正式战报快照及QQ群完赛公告。

120:00整到达的目击请求统一拒绝。比赛结束后裁判终止QQ群实时位置共享。

### 11.6 仅余一名文明或全体淘汰：自动完赛

从T1正式开赛后，每笔可能造成永久淘汰的权威事务或全域批量事件结算完毕时，统计`entry_status='registered' AND flights.status!='eliminated'`的文明数。第一阶段仍有合法重生资格的`returning/preparing/issued`文明均属于存活文明；只有永久淘汰才减少存活文明数。

- **仍有2名及以上：** 继续当前赛程。
- **仅余1名：** 在触发本次淘汰的同一事务中调用统一完赛逻辑，设置`finish_reason='last_survivor'`；该文明获得唯一冠军。
- **存活数为0：** 在触发本次淘汰的同一事务中调用统一完赛逻辑，设置`finish_reason='all_eliminated'`；本场没有存活冠军，淘汰者按规定排序。

自动完赛记录当前`ended_at_game_ms`及真实`ended_at_utc_ms`，将比赛切换为`ended`，关闭攻击、重生、广播、光粒等正式操作，取消未执行的正赛计划事件，并原子封存最终排名与公告待办。对同一批次的全域淘汰先写完全部淘汰记录，再检查存活人数；98:00裁判核验名单在`hunt-finalize`事务中整体结算后检查。完赛事件使用触发事件的稳定ID去重，结果归档与`request_journal`保持幂等。

## 12. 去重目击战绩与终局排名

### 12.1 记录与统计

`attacks`保存每次目击提交的攻击者、目标、有效时刻、`successful`和`valid`。玩家个人实时去重击毁数使用：

```sql
SELECT COUNT(DISTINCT target_player_id) AS unique_sight_kills
FROM attacks
WHERE match_id = :match_id
  AND attacker_player_id = :player_id
  AND successful = 1
  AND valid = 1;
```

只有通过规则判定成功击毁目标飞船的现场目击事件才参与计算；重复击毁同一目标只记1次。光粒、歌者、系统末日、重生超时不产生此数值。裁判撤销违规攻击后，更新`attacks.valid=0`并重算相关统计。

**比赛期间去重击毁数在攻击者本人的`/api/player/self`响应中提供。** 公共排名接口不返回所有玩家的击毁计数；四维观察者解锁后可以在受限的全局态势页面查看已有战绩。没有第65或90分钟全场击毁榜。

### 12.2 永久淘汰记录

每文明当前有效的永久淘汰由`eliminations`中的一条记录表示：`player_id`、`eliminated_at_game_ms`、`eliminated_at_utc_ms`、`committed_at_utc_ms`、`ordering_seq`、`simultaneous_group_id`、`reason`和`source_event_id`。

即时攻击与终局期间违规的人工裁判淘汰，以实际服务器提交时刻为生效UTC。重生超时、65分钟末日等计划事件使用其规定有效时间；第98分钟裁判手动确认的截止资格淘汰统一记为98:00，并映射为生效UTC。`committed_at_utc_ms`单独记录实际落库时间。四维观战180秒等待从有效淘汰UTC开始。

`recordElimination()`统一在同步SQLite事务中退役当前码、写`flights.status='eliminated'`、淘汰日志和私人QQ通知；已淘汰玩家不能被重复淘汰。裁判纠错恢复有效资格时同步撤销当前淘汰状态及观战授权，保留原事件和纠错审计。

### 12.3 正式完赛名次计算

1. 读取正式完赛时仍有参赛资格且未永久淘汰的文明，组成**终局幸存组**；常规完赛点为120:00，自动完赛点为最后一次淘汰事务或终局核验完成时刻。
2. 幸存组按照`unique_sight_kills`从大到小排名；同数共用相同名次。组内最高者是冠军，最高数若有多人相同则并列冠军。
3. 所有已永久淘汰文明都排在终局幸存组之后，按淘汰生效UTC时刻降序；不同普通淘汰事件若毫秒时刻相同，再用`ordering_seq`确定先后；相同`simultaneous_group_id`（含98:00终局资格淘汰批次）则并列。
4. 使用竞赛排名跳号，例如第1、第1、第3、第4。
5. `finish_reason='last_survivor'`时唯一幸存文明获得冠军；`finish_reason='all_eliminated'`时按已淘汰组次序排名，不产生存活冠军。

示例：

```text
第1名（冠军）        C07·归零者    120:00存活，去重目击5
第2名               C12·漂流者    120:00存活，去重目击2
第2名               C19·观星者    120:00存活，去重目击2
第4名               C18·远航者    118:13淘汰，去重目击9
第5名               C02·余烬      109:02淘汰
第6名（并列）       C10·石碑       98:00人工裁决淘汰
第6名（并列）       C05·折叠者     98:00人工裁决淘汰
```

已淘汰文明的目击战绩不能将其排到任何终局幸存者之前。120:00后正式战报可以公开去重击毁数与最终名次；比赛中的普通公开接口提供幸存人数、正式宇宙事件及已永久淘汰者名单，四维观战接口单独提供全局态势。

```json
  "sighting_locked_until_utc_ms": 1800000000000
}
```

**第二次失配，抽中直接出局：**

```json
{
  "accepted": true,
  "result": "no_hit",
  "wrong_count": 2,
  "direct_out": true,
  "flight_status": "eliminated",
  "observer_unlock_at_utc_ms": 1800000180000,
  "message": "本次攻击未命中，你已直接出局。请摘环并返回中控室。"
}
```

两个示例分别展示首次失配与第二次失配抽签出局。时间戳表示字段格式，实际由服务器返回；同一`request_id`重试保持结算一致。所有未命中响应使用中性文字「本次目击未产生击毁」，本人失配数按实际结算结果显示；限速拒绝返回`429`与重试时间。

### 14.4 母星、重生、广播与QQ组件

母星页保存六位字符串及提交版本，裁判按相同版本核验QQ照片。重生页依次引导“摘下所有手环—返航水印照片—离巢50米—领取新配置—安全位置戴上手环—确认出航”，并在各步骤展示当前航次状态和剩余期限。

正式广播和光粒使用单独的六位数字输入框，提交前不鉴定真实母星归属。裁判QQ群与私聊待办分别保存复制和发送状态。90—98分钟玩家页面显示QQ群共享提示与静态终局地图；98:00进入自动核验暂停，显示「终局资格确认中」；总裁判完成资格裁决后，恢复比赛时钟，有两名及以上幸存文明时开放终局目击。

### 14.5 四维观测页面与中控室大屏

永久淘汰时，个人页面显示维度跃迁提示、前往中控室的指引、当前淘汰记录与180秒真实UTC倒计时。到期后显示「宇宙观测」入口，页面轮询只读接口展示当前宇宙态势。

观战内容包括：

- 全部文明的编号、昵称、存亡、母星状态与已审核坐标；
- 当前正常出航文明的两侧手环配置，以及可供解释战况的历史航次；
- 已发生的目击击毁、失配、直接出局、母星清理、广播、光粒、重生及阶段事件；
- 当前有效资源、剩余广播次数与光粒状态、正在返航文明的期限和已发生战绩；
- 公开与授权历史时间线、比赛有效时钟、阶段及幸存人数。

观战内容来源于已有DO SQLite赛事记录和服务端计算结果。未来随机事件安排、HMAC与加密密钥、裁判登录凭证、私人QQ登记照片及裁判指令执行入口不包含在观战响应中。手环码返回可以使用解密后的两侧颜色ID数组，观众需要的是比赛态势而非内部HMAC材料。

官网的比赛数据包括手环颜色码、六位高德位置口令及赛事事件；高德位置口令作为普通字符串存储与匹配。第90分钟起裁判在QQ群内查看位置共享地图，可在中控室投放。游戏官网和观战接口均不接收、存储或处理GPS经纬度及位置轨迹。

中控室优先使用裁判笔记本连接电视、投影或外接显示器，采用扩展桌面：裁判在笔记本管理赛事和使用指令控制台，大屏幕展示只读全局观战页面。持有合法观战权限的死者也能通过个人手机查看相同的赛事数据。观战与裁判工作空间在前端路由、API和会话权限上相互独立。

### 15.4 权限与信息约束

母星审核接口使用`request_id`、`expected_version`、`expected_code`对照玩家最新保存的六位口令及QQ照片。终局裁判接口接收文明编号、枚举裁决原因及`request_id`，`hunt-finalize`的淘汰列表只允许`no_share_at_cutoff/outside_at_cutoff`，`hunt-eliminate`只允许`left_zone/sharing_stopped/location_violation`。请求Schema仅包含这些赛事动作字段；官网只存裁判执行的淘汰与审计记录，QQ共享位置由QQ群承载。

### 15.6 裁判通用指令控制台

**定位。** 裁判GUI承载高频、固定的流程；指令控制台处理精细查询、现场故障、账号及航次修复、事件补结算、资源与参数调整、批量管理等长尾需求。四维观察者在中控室线下讨论并向裁判提案，裁判可使用现有命令实施其中适合的轻度干涉。议会活动不设置线上投票、固定时间点或自动结算逻辑。

**指令风格。** 采用类似Minecraft的斜杠命令、目标选择器与子命令。正式的命名、参数顺序、单位标记、引号规则和BNF由开发实现时确定，支持帮助查询、参数提示、自动补全和可读的错误反馈。以下示例表示预期能力：

```text
/help
/inspect C07
/history C07
/events list
/events inspect EVT-1024
/clock status
/codebook status

/clock pause
/clock resume
/pause_attack @a 60
/resume_attack @a

/player eliminate C07
/player revive C07
/player set C07 homeworld destroyed
/player grant C07 photoid 1
/code reissue C07

/event trigger singer 739216
/event retry EVT-1024
/event cancel EVT-1024

/announce @a "宇宙中出现异常波动"
/tell C07 "请联系裁判"
/reveal @a alive_homeworlds
/reveal @a unused_photoids
/reveal @a kills_last_10min

/schedule 90 /announce @a "宇宙传来了回声。"
/replay @a public_events 3
```

**目标语义。** `C07`为指定文明；`@a`表示全体本场正式参赛者，执行攻击暂停时体现为全场能力效果；`@alive`表示尚未永久淘汰文明；`@dead`表示永久淘汰者；`@random[alive]`表示随机一名存活文明。支持按状态过滤，例如`@a[status=returning]`。开发时将选择器统一解析为全场范围、单个玩家或执行时解析的目标集合，供各业务命令使用。

**命令能力分组：**

| 组别 | 主要职责 | 典型情形 |
|---|---|---|
| 查询与诊断 | 文明、航次、码本、计时器、事件、通知和攻击历史 | 定位异常状态与事务竞争 |
| 比赛控制 | 比赛时钟暂停恢复、全场或指定文明的临时能力限制 | 网络故障、短时宇宙静默 |
| 玩家与资源 | 淘汰与恢复、母星状态、光粒、广播额度、航次和换码 | 纠正错误判定、恢复损坏手环 |
| 事件管理 | 手动触发、补结算、取消、查询、重放已公布事件 | 延迟歌者、失效计划事件 |
| 消息与情报 | 全体公告、定向提示、真实统计、公共事件重播 | 通知、四维低语、母星普查 |
| 参数与效果 | 查询和调整规则参数、施加或撤销临时效果 | 复杂异常、临场低强度现象 |
| 调度与组合 | 延迟执行、条件选择、批量命令与命令宏 | 应急批处理、特殊活动 |
| 审计与修复 | 预览影响、查看事务、纠错执行、记录恢复原因 | 连锁异常调查与追溯 |

**执行模式。** 只读查询直接返回。带副作用的命令先解析与检查权限，可预览目标、当前状态、影响范围及后续业务写入；中高影响操作要求确认与理由。实际执行请求携带稳定`request_id`，服务端完成鉴权、幂等、条件检查和原子事务。命令结果写入`judge_command_log`，状态变化同时写入现有`audit_logs`及相应业务事件日志。

裁判GUI和控制台调用同一业务服务，例如比赛暂停、异常换码和玩家状态纠错由统一的权威操作处理。补结算原有事件沿用原`event_id`实现幂等；主动制造新事件分配独立管理来源ID。历史修复保留已发生信息泄露的痕迹，通过关联事件和审计记录解释后续影响。

**短时攻击静默。** `/pause_attack @a 60`生成一条比赛范围的`attack_silence`临时效果，期限按真实UTC计算。它只关闭目击攻击能力，比赛有效时间、母星状态、其他合法行动和个人错误攻击禁攻按各自规则运行。攻击请求由统一门禁拒绝，不产生失配。到期通过每次读写时的UTC判定自动失效，无须执行恢复指令。`/resume_attack`仅取消对应临时效果，不解除赛事阶段限制或个人禁攻。

**管理自由度与实现边界。** 裁判拥有覆盖比赛状态、事件及参数的高级管理能力。简单命令调用现有服务；复杂纠错可以先生成影响预览，再成批提交业务事务。命令解析器采用注册式处理器与参数校验，服务端不执行任意SQL、JavaScript或shell文本。高风险操作由总裁判权限控制，保留操作原因和可检索的前后状态。

**扩展方向。** 后续可以增加复杂选择器、`/execute if ... run ...`条件执行、命令宏、批量修复、动态规则变量、临时区域效果、消息样式与声音、定时任务取消、事件依赖图和更精确的修复预览。命令语法与实现顺序由开发者在统一风格和业务不变量下安排。

## 16. 事件结算器与故障恢复

### 16.1 单场计划事件模型

单场SQLite的`scheduled_events`以`event_id`唯一标识任务，保存`kind/source_event_id/clock_kind/due_game_ms/due_utc_ms/priority/status/payload_json/attempt_count`及结算、出错时刻。主要事件包括：

| kind | 时基 | 生效点与效果 |
|---|---|---|
| `code_release` | UTC | T0开放本人发码 |
| `match_start` | UTC | T1统一激活全部`ready/reserved` |
| `respawn_timeout` | 游戏有效时间 | 正常击毁后满15分钟，且65:00为硬边界 |
| `song_visit` | 游戏有效时间 | 某正式广播坐标的首次清理到访 |
| `tech_burst` | 游戏有效时间 | 第一阶段第8—55分钟的技术爆炸 |
| `apocalypse` | 游戏有效时间 | 65:00母星同时毁灭 |
| `transfer_start` | 游戏有效时间 | 90:00关闭目击、组织QQ位置共享 |
| `hunt_cutoff` | 游戏有效时间 | 98:00进入终局阶段并自动暂停有效时钟，等待裁判统一完成资格淘汰 |
| `regulation_end` | 游戏有效时间 | 120:00封存存活、去重排名与战报 |
| `judge_delayed_command` | 根据命令约定UTC或有效时间 | 已授权延迟指令及公告 |

个人错误攻击禁攻到期和180秒四维观战解锁，可在每次权限读取时按UTC直接判定；若要求主动发送到期通知，另行建立UTC计划事件。事件必须在SQLite中先持久化，随后才能尝试调用`setAlarm`。

### 16.2 调度器、单Alarm与故障信号

每个Durable Object对象同一时间只有一个Alarm。调度器在每次事务提交后计算：

1. 未结束且未暂停时，获取最近的游戏有效时间任务，将其`due_game_ms`映射为预计UTC到期时刻（考虑历史暂停累计时长）；
2. 获取最早的绝对UTC计划事件（包括T0/T1和已授权的UTC任务）；
3. 选择两类中最早的时间，调用`ctx.storage.setAlarm(dueUtcMs)`，若已到期可安排最近的可执行时刻并立即进入补结算；
4. 若无任何可执行计划，调用`deleteAlarm()`；暂停时不得安排尚未到期的游戏有效时间事件；
5. 在`scheduler_health`记录期望闹钟、最后重排、最后触发、最后成功结算与错误。

**调用顺序约束：** `transactionSync`只负责SQLite事务，`setAlarm/getAlarm/deleteAlarm`在事务提交后以平台Storage API执行；调度器需处理重排过程中的并发请求（使用持久`scheduler_revision`并在`await setAlarm`之后复查最新版本，如已变化再次重排），避免较早的异步操作覆盖更新的最近到期点。不要把请求线程内的JavaScript `setTimeout`或裁判浏览器计时器作为事件唤醒来源。

对一次`setAlarm`失败：记录`status='degraded'`和错误原因；不得声称已成功排程。下一个对象RPC、Alarm重试或总裁判`POST /api/judge/scheduler/rearm`可再次重排；如有关键事件已到期，在统一补结算屏障处理。持续故障必须显示中控室高优先级告警，并按§19安全处置。

### 16.3 Alarm事件处理程序

```ts
// 示意：同一对象内部复用正式业务的结算器
async alarm() {
  const nowUtcMs = Date.now();
  try {
    this.settleDueEvents(nowUtcMs); // 内部按事件逐笔transactionSync、确定顺序
    await this.rearmEarliestAlarm(); // 检查scheduler_revision并修正最新计划
  } catch (error) {
    this.recordSchedulerIncident(error, Date.now()); // 独立的小事务记录错误
    throw error; // 交给平台Alarm重试；事件依赖event_id保证幂等
  }
}
```

`settleDueEvents`按比赛有效时间和计划时刻提取到期事件，依优先级完成事务、公告和审计。65分钟末日在单笔事务中批量生效；98:00的`hunt_cutoff`原子进入`hunt`并创建自动核验暂停，阻止随后游戏有效时间事件越过98:00。终局资格淘汰与恢复计时使用裁判的独立人工指令事务。大量积压事件按有限批次依序结算。

### 16.4 全场暂停、恢复与时间映射

`pause`在DO事务中持久化`is_paused=1`、当前开始UTC与`clock_pauses`新纪录；普通`resume`封闭一般暂停区间，累计暂停长度并解除标志。`hunt_cutoff`事件自动建立`hunt_review`暂停，起始UTC对应98:00有效时刻；仅总裁判的`hunt-finalize`关闭该暂停并结算资格淘汰。用户界面和事件排程都从同一时钟数据计算当前`game_ms`。游戏时基事件在暂停过程中不成熟；恢复时其UTC触发点整体推迟相应暂停长度，不改变原`due_game_ms`。

暂停时已到期但尚未结算的历史事件，在“冻结当前有效时刻”之前先按逻辑顺序补结算。若裁判设备离线而未成功提交暂停指令，服务器仍按运行状态推进比赛；赛后不得用客户端断线时间冒充正式暂停。对于停赛期间的个人禁攻、四维观战解锁与真实UTC管理效果，继续按实际经过时间生效。

### 16.5 幂等、事件竞态和阶段屏障

- **T0/T1：** 全体首航激活使用同一0:00时刻，重复Alarm或RPC不重复激活、不产生额外码。
- **重生超时：** 仅当玩家仍处于本次`returning/preparing/issued`且对应截止未变更时淘汰；已完成合法`launch`或已淘汰则跳过。
- **歌者/光粒：** 母星只有一次从尚存到毁灭的有效更新；后到事件公开结果为“未摧毁现存母星”。
- **歌者边界：** 清理到访时刻必须严格早于65:00，65:00阶段边界先于该时刻的其他系统行为。
- **两人目击：** 同一活跃航次仅第一笔完成的有效击毁获胜；有可信入站UTC和退休UTC的竞速请求可按§7.2豁免。
- **65:00：** 所有仍存母星毁灭；`active`继续最后一命，所有未出航状态永久淘汰，待激活码退役。
- **90:00：** 转场阶段优先于同时刻目击，目击接口直接拒绝且不累计失配。
- **98:00：** `hunt_cutoff`关闭资格窗口，自动冻结游戏有效时钟并维持目击关闭。裁判依据QQ共享地图人工确定淘汰名单，`hunt-finalize`整体结算该组、关闭暂停，再根据剩余文明数量开战或完赛。
- **120:00：** 常规完赛事件先执行，后续攻击、广播与光粒全部拒绝。任一完整永久淘汰结算后存活文明不超过1个时，同笔事务触发提前完赛；批量事件按整个组完成后判断。

### 16.6 服务端时间、淘汰和观战

淘汰事件保留`eliminated_at_game_ms`、`eliminated_at_utc_ms`与`committed_at_utc_ms`：

- 玩家实时动作造成的淘汰：`eliminated_at_utc_ms`为该动作实际权威提交时刻。
- 计划事件造成的淘汰：`eliminated_at_game_ms`为事件规定时刻；`eliminated_at_utc_ms`使用服务器持久化时钟及暂停区间推导出的**原计划有效UTC时刻**；`committed_at_utc_ms`保存真实落库时刻。
- 同一系统事件或同一98:00终局裁判资格批次的淘汰共享`simultaneous_group_id`，排名并列；组内执行顺序不影响名次。
- 四维观察者权限依据当前有效淘汰事件的`eliminated_at_utc_ms+180_000`，与裁判屏幕是否打开无关；纠错恢复合法身份时立即撤销观战读取权。

倒计时以权威服务器状态和时钟返回值计算。系统允许在Alarm延迟时保留准确的逻辑生效时刻，但QQ通知只能由裁判上线后人工发送；不能把“已写通知待办”当成“QQ已送达”。

### 16.7 后台管理与人工操作

管理员界面查询同一DO的事件进度、最近Alarm、积压数量、通知队列和错误日志。`/api/judge/scheduler/health`仅只读；`/api/judge/scheduler/rearm`为高权限显式重新排程接口，调用统一结算器但不伪造历史事件时间；`/api/judge/events/settle-due`为审计化的管理员手动补结算入口。普通玩家无法调用这些接口。

QQ公告、私人提醒、母星核验及终局共享位置判断仍是现场工作人员任务。网页或手机熄屏不妨碍独立Alarm结算；裁判重新打开后台时应完整读回未发送通知及阶段变化。

### 16.8 备份、恢复及临时管理效果

SQLite-backed Durable Objects提供最近约30天的PITR书签恢复接口。赛前与关键阶段按权限生成校验书签及加密战报/重要审计导出，书签和导出文件分开妥善管理。PITR恢复会影响整份对象数据库，正式赛事中只允许总裁判宣布全场暂停、记录证据、审查影响范围后执行；恢复完须核查Alarm重排、事件幂等、码本唯一性、淘汰及通知历史。不可直接用本地重置覆盖正在比赛的对象。

裁判指令统一通过注册式命令服务执行。`attack_silence`等UTC临时效果以`starts_at_utc_ms<=now<ends_at_utc_ms`实时判定；管理员手动禁攻、阶段限制和个人错码禁攻独立叠加，不因单项解除而绕开其他门禁。所有命令执行前均先补结算有效事件，审计保存操作人、理由、受影响行与结果；不执行任意SQL、JavaScript或shell输入。

### 16.9 故障与实战演练清单

必须演练：Alarm安排后关闭全部浏览器；DO对象休眠与唤醒；20秒以上Alarm延迟；事务失败回滚；`setAlarm`重排失败后修复；重复Alarm；比赛暂停并恢复；65/90/98/120各边界±1毫秒；两人同时提交同码；重试同请求ID；设备断网后重复提交；98:00维持禁攻、裁判`hunt-finalize`人工淘汰和恢复目击、终局离圈人工淘汰；180秒观战解锁；裁判通知补看；350码最后一枚与耗尽。

普通玩家的目击输入只依本人现场观察；其他文明的现役手环配置与未公开母星信息通过四维观战接口向已解锁的永久淘汰玩家展示。普通公开API保持既定比赛信息范围。

观战输出按业务含义组织，展示双臂颜色ID、文明、真实母星及事件状态；系统内部密钥、HMAC索引和身份认证信息保留在服务端。中控室大屏幕展示只读态势，裁判管理桌面保留管理操作与私人通讯。

### 17.2 Web安全控制

- 全部写接口校验会话、Origin/CSRF、HTTP-only安全Cookie与参数schema，不接受多余的目击字段。
- 登录令牌与会话保存安全摘要；绝不把公开可枚举的手环码当作口令。
- `code_mac`采用服务端HMAC，规范码加密存储，密钥部署于Cloudflare Secrets；普通日志只保存必要匿名摘要。
- `request_id`唯一码确保攻击、直接出局随机判罚、发码、奖励和通知均能幂等。
- 350码可离线枚举，**不能把小码本或HMAC当作阻止攻击者猜测的安全保证**；规则上的错误攻击高风险、请求节流和人工查违规依然必需。
- 所有正式失配经服务器受理后才累加次数和抽签；格式错误、阶段拒绝和系统并发例外不会受到错误惩罚。
- 使用安全随机源，任何概率直接出局与正常击毁的状态变更都必须原子写入DO SQLite；数据库事务失败不得向玩家先行宣布出局或命中。
- SQL参数绑定、昵称/QQ模板安全转义、不记录完整母星秘密、访问日志不记录完整颜色组合或登录口令。
- 广播、光粒和六位母星匹配按身份提供信息：活人公共公告保留光粒发射者和未披露母星秘密，解锁的四维观战页提供已发生事件的完整赛事态势。
- 裁判撤销错误判罚、异常换码或直接出局纠错必须记录操作者、理由及状态变化。
- 四维观战接口每次检查永久淘汰资格与180秒真实UTC期限，按个人登录会话返回只读数据，并设置私有禁缓存。
- 裁判命令执行入口独立鉴权，预览、审批、请求幂等及状态修复共用业务服务；观战账号不能执行或管理指令。
- 管理命令通过注册式解析与预编译数据库语句执行，不接受任意代码或数据库命令文本。

### 17.3 赛后数据保留

赛前向玩家说明六位母星口令、QQ水印照片、终局QQ群实时位置共享及四维观战的访问范围，并共同确认四维君子协定。比赛结束后由裁判结束QQ群实时位置共享。游戏官网在赛事全过程中只将高德六位位置口令作为普通字符串处理，GPS经纬度和轨迹由QQ位置共享承载并供裁判人工查看。

建议申诉期结束14天内清理不必要的QQ水印照片和裁判另行保管的现场资料。本场码的HMAC及发行历史在比赛和申诉期内保留以保障本场唯一性；归档后清理非必要密文、抽签明细与非公开攻击记录。裁判命令审计、重要异常纠错和正式战报按主办方确定的复核期限保留。公开宇宙事件及匿名统计用于复盘。

## 19. 部署与现场运行

### 19.1 生产部署步骤

1. 创建独立Worker`darkforest-core`，导出`DarkForestMatch`类，使用`new_sqlite_classes`配置SQLite-backed Durable Object，关闭公开`workers.dev`路由。
2. 部署Pages项目，静态页面和`functions/api/*`采用Wrangler构建与部署；Pages配置`MATCH_DO`绑定目标Worker的`DarkForestMatch`类，`script_name`指向`darkforest-core`。生产与预览环境的场次对象ID和密钥隔离。
3. 在Cloudflare Pages的Custom domains添加正式**子域名**，阿里云权威DNS设置CNAME指向Pages项目的`pages.dev`域名。确认HTTPS有效，不更改域名NS。
4. 设置必要Secrets：码HMAC、AES-GCM、会话保护与裁判凭证。密钥只存在Cloudflare服务端，不写入静态构建产物。
5. DO按schema版本初始化SQLite表、索引、权限和`request_journal`；检查`PRAGMA foreign_keys`实际执行结果、核心唯一约束、读写回滚与对象重启后的数据持久性。
6. 初始化正式24个文明账户、每场唯一码本域、身份与裁判角色、母星审核与T0/T1控制；不在正式用户登录前随机生成任何未安排的游戏有效时间。
7. 在校园Wi-Fi、移动/联通/电信与QQ内置浏览器访问自定义域名，逐项测静态页面、Pages Functions、内部DO读写、同一对象跨设备一致性及无浏览器时的Alarm。
8. 配好总裁判的只读调度健康面板、低码余量阈值20/10/0、关键QQ通知积压告警、审计导出和异常时的暂停操作流程。
9. 将正式客户端与裁判界面、部署回滚点、对象PITR书签及账号资料在赛前封存；比赛进行中禁止未演练的代码发布。

### 19.2 赛前流程与官方验收

1. 校验实物手环七色为`BK/WH/GY/YL/OR/SB/PU`；日光、树荫、夜间与典型色觉异常测试都应完成。
2. 离线枚举350个合法码，确认本场永久唯一约束。24人首航占用24个，理论剩余326个。
3. 玩家母星口令与QQ水印照片采用提交版本核验，全部`staged`后由总裁判锁定T0。
4. T0正式开放后每人领取当前双臂配置；全员穿戴确认`ready`后，裁判锁定未来T1。
5. T1到达，由Alarm服务端统一激活全部航次，并通过到期事件屏障验证网页未开启时同样生效。
6. 演练首次失配禁攻300秒、第二次50%淘汰或禁攻900秒、第三次必定淘汰；本场已退役旧码不计失配；同时验证15分钟重生、去重战绩、光粒和每完整60秒歌者；24人局技术爆炸为8次。
7. 演练65分钟母星全灭、90分钟暂停目击、98分钟自动核验暂停及人工淘汰、`hunt-finalize`恢复有效时钟与22分钟终局狩猎、终局离圈或共享中断的手动淘汰，以及120分钟或仅余一名/无人存活时自动完赛。
8. 重复关闭裁判后台、手机锁屏及断网：服务端事件继续执行；重新打开后台后全部未发通知可见。进行暂停、恢复、重启、重复闹钟与调度失败恢复测试。
9. 在中控室检查QQ通知操作、裁判指令预览执行与审计、四维只读观战和投影屏幕，完成安全路线及15分钟真实返航可达性核验。

### 19.3 裁判后台与调度健康

裁判后台查询比赛阶段、有效时间、暂停状态、T0/T1、存活/返航飞船、350码余量、错误处罚、已结算宇宙事件、预定计划、Alarm健康、QQ通知和终局人工淘汰及开战状态。QQ群地图在裁判的QQ会话中显示。

裁判页面轮询比赛态势，恢复前台时重新拉取快照；计划事件由Durable Object Alarms触发。裁判通过QQ发送公告与私聊，从90分钟起监看QQ群位置共享；98:00自动进入终局核验暂停，总裁判核实名单后一次性确认淘汰和开战，参赛文明不超过1个时直接完赛。

### 19.4 故障、补结算与人工裁决

- **单人网络异常：** 该玩家能否行动以服务器已提交动作与资格为准。网络重试使用原`request_id`；若请求结果未知，先查询原请求结果，不能擅自创建第二次攻击。
- **大范围入口故障：** 总裁判在恢复可访问时通过DO执行正式暂停并审查缺失的公告与积压事件；只有已成功提交的暂停时段计入权威游戏时钟，必要时依据审计作统一裁决。
- **Alarm异常：** 优先检查`/api/judge/scheduler/health`，受控执行`rearm`并检查补结算的事件生效时刻；不允许未核验的重复事件发奖或重复淘汰。
- **QQ共享地图整体异常：** 转场期间由总裁判暂停有效时钟；98:00核验期间沿用系统自动暂停。QQ恢复后裁判完成资格核验，并通过`hunt-finalize`统一执行淘汰与开战/完赛。
- **人工战斗裁决：** 全场暂停并建立可追踪的人工记录，按七色集合归一化、旧码无效、首次禁攻5分钟、第二次等概率抽签或禁攻15分钟、第三次淘汰的规则执行。
- **存储异常或误操作：** 利用限权审计、PITR书签及加密导出制定恢复方案；必须评估已发送QQ通知、已公开秘密、排名、码本和Alarm重排的一致性，不能仅恢复某张表。

任何影响核心公平性的故障必须给总裁判明确的“暂停/保持暂停/恢复”建议与可审计的恢复流程。赛后归档、隐私清理和通知队列保留期限按§17执行。

## 20. 测试矩阵

### 20.1 母星待审核与统一首航

- [ ] 玩家提交`001234`为`pending`，保存版本；QQ复制文本从已持久化口令与版本生成。
- [ ] 重交口令版本递增，裁判持其他本审核失败；重复六位口令只有一人可获得`verified`。
- [ ] 母星未审核、未离巢50米、七色材料不齐的玩家不能进入`staged`。
- [ ] 全部正式玩家`staged`后才能锁定T0；T0前任何网页/API都不得返回其首航码。
- [ ] T0后领取唯一双臂配置、码`reserved`，重试、并发或断网不重复发行。
- [ ] 玩家正确佩戴3或4条并点击就绪才成为`ready`，全部`ready`之后才能锁定T1。
- [ ] T0—T1所有目击、广播、光粒均被服务器拒绝且不计失配。
- [ ] T1到达后无论玩家是否在线，全部`ready/reserved`同时从比赛0:00生效；多次触发幂等。
- [ ] 24人实际佩戴、等待及确认耗时通过现场压力测试，不延误统一赛程。

### 20.2 七色手环码、唯一性与容量

- [ ] 7位颜色ID严格稳定映射`BK,WH,GY,YL,OR,SB,PU`，不能由前端任意增加或重新排序。
- [ ] 完整枚举`2+1`105枚、`2+2`105枚、`3+1`140枚，总共350枚，互不重复。
- [ ] `arm_a`与`arm_b`交换时规范键不变，同臂颜色ID顺序打乱也不变。
- [ ] 空臂、同色重复、非法颜色、`1+1`、`3+2`、`4+0`、`4+1`等非法形状均被拒绝。
- [ ] 24人初始发行之后剩326枚；连续发350枚无重复，第351次返回容量耗尽并向裁判告警，不复用历史码。
- [ ] 旧码`retired`、待激活作废、异常退役和退赛码均占用唯一簿；按两侧颜色集合的唯一键判定。
- [ ] 两人并发领同一未用码时，只有一个事务成功；另一人重选仍未用码，不误发两张重复码。
- [ ] 正式参赛账号仅能通过本人页面读取自己的手环配置；四维观察者满180秒后可通过专用只读接口查看全局现役码；公共API不提供完整发码簿。

### 20.3 攻击与直接出局

- [ ] `{request_id,arm_a:["BK","OR"],arm_b:["WH"]}`能与左右互换的同一配置命中同一目标；同臂顺序无影响。
- [ ] 目击请求包含固定的请求ID和两侧颜色数组，Schema对其他字段返回格式错误。
- [ ] 有效命中只击毁一个`active`飞船、退役目标码、发放该目标真实母星情报并增加正确的去重战绩来源。
- [ ] 本人当前或历史码、本场他人已退役旧码均为无效目击且不计失配；未发行码、他人待激活码在正式受理且未命中时累计失配。
- [ ] 并发抢先击毁在有可信证据时分类为`lost_race`；其他本场退役旧码分类为`retired_code`，两类均不计失配。
- [ ] 第一次失配禁攻300秒；第二次抽签0—49直接出局、50—99禁攻900秒；第三次失配直接出局。
- [ ] 直接出局的玩家母星（如尚存）与现役飞船同步注销、不能进入重生、不产生任何别人的目击战绩。
- [ ] 直接出局记录真实游戏时刻并按原终局淘汰顺序排名；若两人同时因独立事件出局，使用原事务/时间排序规则。
- [ ] 禁攻玩家仍可被攻击，广播/光粒等其他合法行动不被意外封锁；禁攻跨重生持续。
- [ ] `wrong_count`跨航次、成功攻击、冷却结束保持累计；未受理格式错误、重复ID、冷却中请求不加失配。
- [ ] 同一`request_id`重复到达抽签值、直接出局和冷却时间完全相同；两个独立正式受理错误请求各自按序处罚。
- [ ] 第二次失配的安全随机抽签按0—99等概率分布；大量模拟中直接出局与禁攻15分钟各占约50%，同请求ID重试保留原抽签结果。
- [ ] 成功与错误攻击互斥，多请求并发不产生两次目标击毁或一次错误多次判罚。
- [ ] 未命中页面统一显示「本次目击未产生击毁」及本人累计失配、适用禁攻期限和淘汰提示；后台详细结果分类按裁判权限查询。
- [ ] 通用4秒间隔、60秒最多10次、单场120次审核阈值适用，且执行在码查询之前。

### 20.4 正常重生、宇宙阶段与排名

- [ ] 正常被目击击毁后立即摘下全部比赛手环、返航拍照并发QQ、离巢50米、领新码、重新佩戴、确认出航。
- [ ] 15分钟截止前完成`launch`有效；正好截止或65:00到期的请求先处理淘汰；不设置累计重生次数预算。
- [ ] 直接出局者不能通过自行返航、按钮操作或当前母星仍有记录而重生。
- [ ] 母星被歌者或光粒摧毁时，已经正常出航者保持当前码进入最后一命；准备中的玩家直接淘汰。
- [ ] 六位坐标保留前导零；广播每人最多2次、歌者每完整60秒独立5%、按开赛人数动态确定的技术爆炸和光粒正确结算。
- [ ] 同一目标不同航次被同一攻击者多次击毁，只增加一次不同文明数；直接出局不计任何目击击毁数。
- [ ] 65:00全域末日、90:00关闭目击、98:00自动冻结游戏时钟并由总裁判单事务裁定资格、之后保持完整22分钟狩猎和持续人工执裁，以及120:00常规完赛均正确。
- [ ] 第一阶段剩余一名`active`与一名`returning`时继续比赛；后者最终淘汰后自动完赛。普通单笔攻击、超时及65:00批量淘汰均先完成完整事务，再按人数自动完赛。
- [ ] 98:00核验批次仅余一人或无人存活时直接完赛，不开放新目击；同批淘汰者并列，最终战报和剩余计划事件状态一致。

### 20.5 颜色识别、系统与现场执行

- [ ] 七色手环必须为同供应商同规格；普通视觉和至少两类典型红绿色觉异常观察者分别在日光、树荫、夜间实测。
- [ ] 白/灰、黄/桔、黑/天蓝、天蓝/紫等重点混淆组合逐对记录识别率和辨认时间；网页色块含中文标签。
- [ ] 从活动最远合法地点正常步行完成返航、拍照、离巢、换码与确认能在15分钟内完成。
- [ ] 阿里云DNS管理的Pages自定义子域名，在校园Wi-Fi、移动、联通、电信和QQ内置浏览器均能访问静态页面、Pages Functions及内部DO读写。
- [ ] 验证关闭所有浏览器、裁判手机锁屏之后，Alarms仍能主动唤醒并执行阶段事件；实际提交UTC与事件有效时间分别保存。
- [ ] 验证DO对象重启后SQLite状态、事件队列和码本不丢失；重复Alarm及RPC不会双重结算。
- [ ] 验证`setAlarm`登记失败、延迟与重排修复的监控告警，以及暂停时任务冻结与恢复时重新排程。
- [ ] 已发行码HMAC、加密配置、服务端密钥、未来随机事件和非公开母星不泄漏到公共API、缓存或普通日志。
- [ ] QQ通知及水印照片审核版本正确写入；终局服务器只记录裁判提交的文明编号、淘汰原因、执行时间及审计，不保存QQ共享地图、经纬度或轨迹。

### 20.6 四维观战与裁判指令控制台

- [ ] 所有永久淘汰来源原子记录比赛游戏时刻和真实UTC时刻；未满足180秒时只返回观战倒计时。
- [ ] 全场暂停期间，180秒观战解锁仍按真实UTC推进；重生中的玩家不会提前获得四维权限。
- [ ] 死者账号满180秒后可查询真实母星、现役手环配置、已发生战绩和事件；普通活人账号不能读取这些数据。
- [ ] 观战接口无法调用攻击、广播、光粒、重生、账号管理、裁判指令及其他写操作。
- [ ] 裁判恢复一名被误淘汰玩家的正式资格后，其观战接口立即失效；纠错时的航次、码、名次及记录保持一致。
- [ ] 观战响应不包含HMAC密钥、管理员凭证、未来随机安排、私人QQ照片；响应与CDN缓存配置保持私有禁缓存。
- [ ] 查询类命令返回当前权威状态；含副作用命令提供预览，确认执行后有唯一请求ID及可核查的审计记录。
- [ ] `pause_attack @a 60`按真实UTC产生比赛范围的临时效果，赛事有效时钟照常运行，不触发失配，并按时自动失效。
- [ ] 临时静默、错误攻击禁攻、手动禁攻、90—98分钟转场及98:00核验暂停的限制独立叠加；任一有效限制均拒绝目击。
- [ ] 公开统计与高维公告不消耗玩家正式广播额度，也不安排歌者；历史事件重播不重新结算事件。
- [ ] 玩家状态/资源修复、事件补结算、换码及异常批量处理调用受保护的业务服务，复用裁判GUI的核心事务。
- [ ] 控制台指令输入错误、重复提交、网络重试、越权调用、并发操作及数据库失败都能给出一致结果。
- [ ] 裁判可线下采纳或拒绝四维提案，不建立定时议会和自动投票结算；中控室屏幕、观战手机与正式操作设备同时可用。
